# Автоматизация начисленного ФОТ из 1С

## Подключение начислений к service2

Первый источник OData сохраняет только начисленный ФОТ за месяц. Данные
выплат, задолженности, фамилий и подразделений из агрегатов не выводятся.
Для него добавлены `PayrollAccrualMonth` и отдельный тип активной версии
`payroll_accrual`. Таблица `PayrollRow` и подтверждение старого Excel-отчёта
сохраняются для подробных расчётов с персоналом.

Путь в приложении: Финансы → ФОТ → загрузки → получить начисления из 1С →
выбрать месяц → проверить сумму и охват организаций → подтвердить.
GET страниц не обращается к 1С и не создаёт импорты. Получение и подтверждение
выполняются POST, с проверкой `can_import_payroll`, активного доступа к
организации и соответствия `ONEC_ODATA_TARGET_ORGANIZATION_ID`.

В финансовой сводке и сводке начислений раздела ФОТ за каждый месяц выбран
один источник: подтверждённый OData имеет приоритет; при его отсутствии
используется активный Excel. Они не складываются за один месяц. История
Excel и его выплаты/остатки остаются отдельным отчётом. Смена активной
версии любого из этих источников после получения предпросмотра блокирует
устаревшее подтверждение. Повторное подтверждение не возвращает старую
версию в активное состояние.

## Настройки источника и включение

Используются существующие `ONEC_ODATA_BASE_URL`, имя пользователя, пароль,
`ONEC_ODATA_ORGANIZATION_GUIDS`, целевая организация приложения и доверенные
CA из `SSL_CERT_FILE`/`SSL_CERT_DIR`. Дополнительно обязательны:

- `ONEC_ODATA_PAYROLL_CURRENCY_GUID`: GUID валюты в конкретной базе 1С;
- `ONEC_ODATA_PAYROLL_CURRENCY_CODE=RUB`: явное подтверждение администратора,
  что выбранный GUID обозначает российский рубль — валюту текущей сводки.

Не копируйте GUID из примеров и не определяйте валюту по равенству двух сумм.
Проверьте её в справочнике валют вашей базы. Без настройки импорт закрыт.
Все группы должны соответствовать выбранной валюте; курсы и пересчёт валют
на этом этапе не реализованы. Смена источника, списка организаций или валюты
требует нового предпросмотра.

Первая версия принимает наблюдаемый `Тип=Начисление`. Начисления сверяются
по каждой организации с `Receipt` документа `НачислениеЗарплатыУНФ` в
регистре расчётов с персоналом. Неизвестный тип/документ, неполный ответ,
расхождение, чужая организация, другая валюта или недопустимая точность суммы
останавливают импорт. Пустой месяц не замещает текущую версию нулями.
Организации без строк показываются до подтверждения; оператор отдельно
подтверждает охват. Отсутствие строк не доказывает нулевой ФОТ организации.

## Запуск без Excel и подготовка расписания

После штатного обновления кода, применения миграции и проверки настроек
доступна management command `sync_onec_payroll`. Организация здесь — ID
организации **service2**, пользователь — действующий пользователь приложения
с правом импорта ФОТ. GUID организации 1С в эти аргументы не подставляется.

Пример с условными значениями (заменить ID и месяц):

```bash
../venv/bin/python manage.py sync_onec_payroll --organization 123 --user 456 --month 2025-01
```

По умолчанию создаётся только предпросмотр, активная сумма не меняется.
Для заранее согласованного применения используется та же команда с
`--confirm --accept-coverage`. Второй флаг означает явное принятие охвата
настроенных организаций, в том числе показанных без строк; его нельзя
считать автоматическим доказательством полноты отчёта.

Повторный запуск с неизменённым ответом использует действующую версию;
новые данные создают новую версию, а ошибка сохраняет прежнюю. Вывод команды
содержит только ID загрузки, её статус и месяц. Пароли и ключи в командную
строку не передаются. Права и настройки проверяются при каждом запуске.

Команду можно использовать в cron после проверки на hosting. Расписание
в рамках этой разработки не установлено; окно обновления прошлых месяцев
нужно выбрать с учётом поздних перерасчётов. На текущем этапе программа
получает один явно указанный месяц за запуск.

## Сохранность и ограничения

Предпросмотр хранится как приватный JSON без индивидуальных начислений.
При подтверждении заново проверяются SHA256, размер, версия формата,
организация, месяц, настройки источника, контрольные суммы и активные версии.
Изменение активного месяца и запись проекции выполняются одной транзакцией
под блокировкой организации. Ошибка не заменяет действующий ФОТ.

Чтение 1С запускается в отдельном процессе с общим ограничением 65 секунд;
внутренний Linux CLI также ограничен 60 секундами. Медленный ответ не может
бесконечно удерживать запрос Django. Учётные данные передаются окружением
дочернего процесса, не аргументами команды и не журналом ошибок.

Миграция `0100_payroll_accrual_month` добавляет новую таблицу и варианты
типов отчётов; существующие строки зарплаты не пересчитывает. Перед production
нужны проверка pending migrations, резервная копия и штатный reviewed deploy.
Изменения этой задачи не запускают миграции или запись на hosting сами.

Единая кнопка обновления продаж/ДДС пока не включает ФОТ. Первый запуск
месяца и подтверждение выполняются отдельным путём ФОТ. Настройка фонового
расписания относится к последующему включению на проверенном сервере.
OpenAI API и токен доступа Codex загрузчику не нужны.

## Проверенная исходная точка

Задача владельца от 9 сентября 2026: заменить ручную загрузку Excel данными
из существующего подключения к 1С. Проверен GitHub main
`d29e85b6e616afb17a2788c036b6517424840735`; это не проверка рабочей базы.

Сейчас `odata_unified_sync.py` поддерживает только продажи и ДДС. Читатели
используют `AccumulationRegister_Продажи_RecordType` и
`AccumulationRegister_ДвиженияДенежныхСредств_RecordType`. Эти данные не дают
достоверного начисленного ФОТ. Выплата зарплаты не равна её начислению.

Существующий путь ФОТ: XLSX → проверка контрольных итогов → предварительный
просмотр → подтверждение → `PayrollRow` → активная версия отчёта за месяц.
Строка содержит сотрудника, подразделение, месяц, начальный остаток,
начислено, выплачено и конечный остаток. Все четыре суммы обязательны.
Отчёт отдельно суммирует начисления и выплаты.

## Недостающий контракт источника

Первоначально в репозитории не было подтверждённой схемы зарплатного
регистра/документа 1С. Владелец получил `$metadata` через действующее
подключение и передал поля двух регистров, справочника видов начислений
и документа начисления зарплаты. Наблюдаемый контракт зафиксирован в
`docs/1c-payroll-source-contract.md`. Затем владелец выполнил чтение месяца и
подтвердил совпадение начислений с привычным отчётом 1С.
Диагностика выводит технические имена и типы полей, без значений строк,
фамилий, сумм и реквизитов подключения. Название подходящего регистра ещё
не подтверждает смысл начислений и полноту его данных.

`scripts/inspect_onec_payroll_schema.py` запускается отдельно от Django из
существующего virtualenv на Linux. Параметр `--app-dir` указывает каталог
приложения; настройки читаются из его `.env` и environment процесса.
Скрипт выполняет единственный HTTPS GET `$metadata`, не запускает Django,
не подключается к БД и не запрашивает строки регистров. Перенаправления
запрещены; размер ответа и время выполнения ограничены.

По умолчанию выводится список кандидатов по техническим именам. Параметр
`--entity ИМЯ_ИЗ_СПИСКА` добавляет поля выбранной сущности и связанные типы;
параметр можно повторить. Пустой список означает только отсутствие совпадений
эвристики в опубликованной схеме, а не отсутствие начисленной зарплаты в 1С.
В HTTP 403/404 или ошибке схемы также нет свидетельства о нулевом ФОТ.

Первый запуск владельцем проверил SHA256 файла успешно, затем завершился
`METADATA_CHECK_FAILED`. Это подтверждает запуск диагностического файла,
но не подтверждает получение ответа 1С и не определяет причину сбоя.
Диагностика ошибок должна показывать этап и ограниченный технический код
причины (например, DNS, TLS или timeout), сохраняя скрытыми исходные тексты
исключений, endpoint, credentials и содержимое ответа. Проверка сертификата
TLS и запрет перенаправлений остаются обязательными.

Повторный запуск владельца уточнил сбой: `metadata_open / TLS_CERTIFICATE`.
Это ошибка проверки TLS-сертификата, а не ответ об отсутствии зарплатных
данных. Сам код не устанавливает, истёк ли сертификат, не хватает ли
доверенного центра или неверно имя сервера.

Обнаружено отличие диагностики от Django-приложения: приложение вызывает
`load_dotenv`, а диагностика ранее читала `.env` только в словарь, поэтому
параметры `SSL_CERT_FILE` и `SSL_CERT_DIR` из файла не попадали в TLS-клиент.
Теперь эти параметры из объединённых настроек передаются в проверяющий
SSLContext явно; environment процесса сохраняет приоритет над `.env`.
Если параметры не заданы, сохраняется стандартное хранилище доверия Python.
Ошибка заданного хранилища останавливает проверку, без обхода TLS или
автоматической подстановки другого источника сертификатов.

Наличие этих настроек на production и причина его ошибки пока неизвестны.
При повторном отказе выводится только числовой `verify_code`, если он доступен;
исходные сообщения сертификата, hostname и пути не раскрываются.
Поведение контекста и кода проверки описано в
[документации Python SSL](https://docs.python.org/3/library/ssl.html#ssl.create_default_context).

```bash
../venv/bin/python -B scripts/inspect_onec_payroll_schema.py --app-dir "$PWD"
```

При запуске без обновления приложения диагностический файл нужно брать по
фиксированному SHA из GitHub в отдельный временный файл и проверять его SHA256.
Не требуется объединять PR, выполнять `git pull` или перезапускать Passenger.

Перед реализацией импортера нужно установить:

- источник начислений, выплат и остатков либо явный отдельный контракт
  для загрузки только начислений без выдуманных нулевых остатков;
- организацию, месяц начисления и его отличие от даты выплаты/регистрации;
- устойчивые идентификаторы сотрудника и строки, подразделение;
- правила проведения, отмены, сторно и перерасчётов;
- способ подтвердить полноту месяца и сверить итог с отчётом 1С.

## Критерии готовности автоматической загрузки

Импортер должен сохранять организационные ограничения, проверку прав,
сопоставление сотрудников и выбор активной месячной версии. Повторная
загрузка не должна удваивать ФОТ. Ошибка чтения, неполный ответ или отсутствие
зарплатного источника не должны заменять существующий отчёт нулями.
Изменённые данные 1С должны создавать проверяемую новую версию, а исходный
Excel-импорт должен оставаться пригодным для сравнения и истории.

Техническая схема и сверка начислений одного реального месяца подтверждены
владельцем. Рабочая загрузка новой версии в service2 ещё не выполнялась.
Доступ к GitHub не даёт агенту доступ к 1С.
Диагностический этап не требует миграций или перезапуска приложения.
Разработка и независимое ревью продолжаются в активной сессии Codex;
создание токена workspace и отдельно оплачиваемый OpenAI API не требуются.
