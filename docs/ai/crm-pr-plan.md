# CRM: последовательность небольших PR и приёмка

Основание: [архитектура этапа 0](crm-stage-0.md),
[перенос и права](crm-migration-access-plan.md), [ТЗ 0.4](crm-spec-v0.4.md).
Номера PR-01…PR-30 — плановые, это не созданные GitHub pull requests.
Этап 0 завершает подготовку; реализация начинается отдельной задачей.

Каждый PR содержит один проверяемый результат, целевые тесты, описание флага и
совместимости. Новые миграции поставляются вместе со своим агрегатом, без
одной гигантской схемы заранее. Порядок ниже линейный по строкам таблицы, а не по числам в идентификаторах:
PR-01–PR-13 → PR-15–PR-18 → PR-14 → PR-19–PR-30. По умолчанию PR зависит
от предыдущей строки; значимые дополнительные зависимости указаны явно.
Стабильные номера PR сохранены: это по-прежнему 30 плановых пакетов. Если diff
перестаёт быть обозримым, его делят на schema/read и command/UI, сохраняя порядок
и те же приёмочные gates. Объём оценивается после инвентаризации, сроки здесь
не выдумываются.

Обозначения ревью: R — права, M — миграции, F — финансы; содержание независимых
проверок описано в плане переноса. Для каждого изменения этих областей ревью
обязательно, даже если таблица отмечает только основной риск. CI выполняется
на финальном head; после существенного исправления повторяется соответствующая
проверка. Общие регрессии существующих сценариев включаются в CI.

Недоступная операция имеет явный статус, а не второй legacy writer.

PR-25 нельзя формально закрыть успешным тестом фикстур, если подтверждённый источник
расчётов по реальному контракту чтения не установлен. В этом случае результат —
доказанный пробел источника и точная дополнительная задача; PR-26/27 не включают
успешное закрытие. Это зависимость будущей реализации, не блокер документации.

PR-22 даёт операционный остаток, а подтверждение частичного **учётного** оформления
завершается только после PR-23/24. До этого сводка не называется финансовым фактом.
Подобным образом один канбан PR-12 не является завершением CRM.

## 3. Сквозная приёмка и контроль полноты

1. Новый внешний отвеченный звонок → предварительный лид назначен сотруднику →
   квалификация → КП с выбранным вариантом → открытая стройка → одно действие
   Александра → выполнение → подтверждённый полный расчёт → явное закрытие.
   Повтор webhook, поздний ответ и двойной клик ни на одном шаге не дублируют факты.
2. Два менеджера берут свободный лид → один владелец; второй видит командную
   карточку, но не получает право менять чужое/слушать private по факту просмотра.
3. Сервисник без визита берёт 3 канистры под A → переносит назначение количества
   на B → доставляет 2, возвращает 1 → менеджер видит 2 к оформлению по B →
   связывает реальный разовый договор → частичная реализация оставляет остаток;
   повтор сводки/импорта не создаёт новую сделку или вторую поставку.
4. В одной сервисной потребности химия доставляется без КП, насос ждёт
   согласования, включённая работа выполняется по основному договору. Завершение
   supply-задачи не закрывает коммерческий заказ/основной договор.
5. Договор на N месяцев → проверяемые строки нескольких реализаций покрывают
   конкретные периоды → расчёт основного договора подтверждён → D10 допускает
   закрытие при отдельном долге химии. Пропуск месяца, общий нераспределённый
   платёж или только no_current_receivable не допускают успех.
6. Новая активная версия отменяет строку после закрытия → актуальное расхождение
   видно, прежнее основание закрытия сохранено; денежный прогноз и прямые затраты
   не изменили смысл; новое исполнение не создано.
7. Legacy перенос запускается дважды с остановкой между пакетами → те же IDs и
   связи, 0 повторных сделок; безопасное выключение новых writes сохраняет входящие;
   прежний service-календарь/задачи продолжают работать.
8. Ручной тендер выигран → контракт и исполнение у той же сделки. Фильтры Q13
   не настроены → нет автоматического признания «подходит» или исключения.
