## Что GitHub выполняет сейчас

На pull request в main основной workflow выполняет Django checks, migration
dry-run, четыре последовательные группы Chromium acceptance, затем общий
серверный test suite. Разделение по изменённым подсистемам и параллельные shards
этого suite пока не реализованы. Это относится и к docs-only PR: отсутствие
локального Django-прогона для документации не выключает GitHub CI.

Отдельный management-finance-mysql.yml использует path filters и выполняет
широкий набор совместимости на MySQL, включающий CRM, контакты, коммуникации,
доступ, миграции и финансы. Название задания не означает «только финансы».
Он может идти параллельно основному workflow. Браузерные классы общего suite
пропускаются без специальных flags; это не повтор всех браузерных сценариев.

Для PR #495 успешный основной прогон занял 51 минуту: около 39 минут общий suite
и около 10½ минут браузерные группы. Число 4808 тестов и 135 пропусков относится
только к [этому запуску](https://github.com/borovikov88/service2/actions/runs/44223192392),
а не задаёт постоянный лимит или состав тестов.

scope job и aqualine22_scope.py определяют маршрут публикации изолированного
калькулятора. Они не выбирают набор CRM-тестов по затронутым файлам.
Ускорение тестов требует отдельного проверяемого изменения workflow/scripts:
выбор подсистем с зависимостями, полный fallback для общего/неизвестного diff,
параллельные группы и сохранение обязательных checks. До реализации нельзя
объявлять эти оптимизации включёнными или вручную пропускать текущие gates.

## Повторное использование результата PR

Успешный PR записывает в имени заключительного шага Git tree/commit проверенного
checkout. После merge test job может использовать это доказательство, если:

- всё дерево нового main совпадает с проверенным деревом;
- PR/workflow принадлежат этому репозиторию, latest run/attempt успешен и не старше суток;
- workflow и проверяющий script не менялись относительно первого родителя main;
- подтверждены merged PR, единственный успешный test job/marker и Git parents/tree.

Проверяются публичные metadata GitHub; artifact/log payloads не используются
как доказательство для этого механизма. Ошибка доступа/API, несовпадение,
неоднозначность, fork, изменение политики или workflow_dispatch дают обычный
полный CI. Другие credentials, секреты и обход 403 не являются fallback.
В PR #495 это использование уже сработало: повторного 51-минутного прогона после
merge не было. Required checks и production guards при этом сохраняются.

## Разрешённая последовательность выпуска

Обычный merge и protected deployment продолжаются без повторного вопроса,
когда задача и действующая авторизация владельца включают этот выпуск, её
область ясна, final head проверен, CI зелёный и обязательное независимое ревью
не содержит нерешённых замечаний. Авторизация не заменяет текущие branch,
environment и preflight guards и не разрешает новый scope.

Новый конкретный сбой CI/review/preflight сначала разбирается и исправляется
в рамках задачи. Решение владельца требуется при выходе за авторизацию,
разрушительном/recovery-действии, недоступных исходных данных или реальной
развилке. Само ожидание CI не создаёт потребности в новом «продолжай».

После merge используется точный tested commit. Workflow выполняет preflight,
проверяет актуальный origin/main и состояние checkout, получает штатные общие
блокировки, создаёт проверенный приватный backup БД, обновляет приложение и
проверяет HTTP 2xx. Название environment само по себе не доказывает, какие
дополнительные approval/ruleset настроены; это проверяется по текущему GitHub.

При коде 75 из-за занятого deployment/call-analysis lock дождаться завершения
держателя. Не удалять lock, не останавливать production worker и не дублировать
запуск. Перед повтором сверить текущий run/attempt; если тесты уже прошли и
причина подтверждена, повторить только неуспешное deploy job тем же штатным путём.

Разрешение на обычную публикацию не распространяется на несогласованные
миграции, импорт, изменение production-данных, классификаций, ролей, секретов,
внешних сообщений/публикаций и инфраструктуры. Для этого нужна явно поставленная
область задачи и соответствующая авторизация. Не обходить guards прямым push/SSH.

Разработка/review используют выбранный владельцем путь ChatGPT/Codex.
API-review/publisher и старый poller не считаются работающими через эту
авторизацию. Не добавлять платный API fallback или извлечение browser credentials.

Ниже сохранены инструкции настройки и специальные runbooks. Датированные
проверки сентября/октября внутри них не подтверждают текущие настройки доступа.

## Однократная настройка GitHub

Для разработки используется активная Codex-сессия и штатный GitHub connector.
Для независимого GitHub-ревью используется Codex Code review в рамках плана
владельца. Нужные настройки и фактическая проверка описаны в `codex-direct-flow.md`.

Ранее настроенные `SERVICE2_REVIEW_TOKEN` в Environment `review`,
`OPENAI_API_KEY` и серверные `GITHUB_DEVELOPMENT_REVIEW_*` не являются
авторизацией тарифного Codex. Retired workflow больше не получают эти секреты.
Данный переход не удаляет секреты и не изменяет production `.env`: могут
существовать другие потребители. Не создавать новые API-ключи для этого цикла.

Создать Environment `production` и repository/environment secrets:

- `DEPLOY_HOST` — SSH hostname;
- `DEPLOY_PORT` — SSH port (можно оставить пустым для 22);
- `DEPLOY_USER` — отдельный deployment user;
- `DEPLOY_APP_PATH` — абсолютный путь к checkout, содержащему `update.sh`;
- `DEPLOY_SSH_KEY` — закрытый ключ ограниченного deployment user;
- `DEPLOY_KNOWN_HOSTS` — заранее проверенная строка host key, не результат
  отключения `StrictHostKeyChecking`.
- `DEPLOY_HEALTH_URL` — обязательный HTTPS URL без userinfo, query и fragment для
  ограниченной проверки после перезапуска; успешным считается только HTTP 2xx.

Публичный ключ должен иметь только права, необходимые для обновления этого
приложения. Production checkout должен иметь read-доступ к GitHub `origin` и
существующие `.env`, `../venv` и `../tmp`. Секреты не записываются в Git.

После первой настройки workflow нужно запустить на тестовом PR, независимо
проверить его, merge выполнить через защищённый `main`, затем проверить GitHub
deployment log и фактический health приложения. До этой проверки схема считается
подготовленной, но не доказанной на хостинге.

Перед изменяющим SSH-шагом workflow запускает `update.sh` в режиме `preflight`.
Он использует read-only `git ls-remote`, проверяет точный `origin/main`,
Passenger-layout, virtualenv, writable `tmp` и допустимость состояния checkout.
Он не выполняет fetch/checkout/pip/migrate/collectstatic/restart. Найденные
неизвестные локальные изменения не выводятся и не удаляются: deployment
останавливается.

## Проверка доступа из GitHub Actions без deployment

Workflow `Check hosting connection (no deploy)` проверяет введённые secrets
отдельно от изменяющего pipeline. Он запускается при попадании его workflow или
runner в `main` и вручную через Actions → этот workflow → Run workflow (`main`).
На PR и на других refs job с Environment `production` не запускается. Checkout
берётся по точному SHA события, GitHub token имеет только `contents: read`.

Runner `.github/scripts/check_hosting_connection.py` требует все семь значений
`DEPLOY_*` (для этой диагностики порт указывается явно, обычно `22`). Он проверяет
формат ключа и наличие pinned host key, входит по указанному identity без SSH
agent/password и без отключения проверки сервера, читает пользователя и HEAD,
проверяет структуру каталогов и версию Python/Django без загрузки настроек
приложения, затем требует фактический HTTPS 2xx по health URL без redirects.
Закрытый ключ хранится только во временном файле runner с правами `600` и
удаляется после проверки, включая ошибки.

Успех обозначается `HOSTING_CONNECTION_CHECK_OK (no deployment performed)`.
Этот результат фактически получен 5 сентября 2026 года в повторном запуске
Actions run `33967180783`: SSH, layout, Python `3.13.2`, Django `5.1.6` и
`HEALTH_HTTP=200` подтверждены. Production по этому запуску оставался на
`1cc6e08`; приложение не обновлялось.
Он подтверждает доступ из runner и передачу secrets, но не совпадение production
HEAD с `main`, не полный deploy preflight, не финансовые отчёты и не deployment.
Этот workflow не вызывает `update.sh`, fetch/checkout на хостинге, миграции,
импорт, collectstatic или Passenger restart. GitHub может отображать использование
Environment как deployment activity; это не означает обновления приложения.
Изменяющий workflow повторяет CI для точного commit в `main`, затем выполняет
deployment preflight и health-check; GitHub APPROVED отдельного аккаунта не
требуется. Проверка branch protection через GitHub CLI на 8 октября 2026 года
вернула `Branch not protected`; обязательные PR checks сейчас не обеспечиваются
настройкой защиты `main`.

## Собранная статика в существующем checkout

`STATIC_ROOT` — `public_static`, а исходники приложения находятся в
`pool_service/static`. В репозитории исторически отслеживается часть собранных
файлов: после `collectstatic` Git может показывать обычные результаты сборки как
местные изменения. В сессии владельца все 21 показанный файл совпали с
исходниками. Это не основание игнорировать весь `public_static`.

Preflight допускает изменённый или untracked файл в `public_static` только если
это обычный файл без symlink-компонентов, а соответствующий исходник в
`pool_service/static` совпадает и с ним, и с обычным Git blob текущего HEAD.
Staged changes, удаления, неизвестные файлы и несовпадения блокируют deployment.
`backups/` не получает исключения; её содержимое сохраняется на сервере и
требует отдельной сверки, без отправки в репозиторий.

В изменяющем режиме после fetch проверка повторяется с доступным точным target
commit. Коллизии untracked output с отслеживаемым target path, удаление или
смена типа соответствующих исходников/отслеживаемых output блокируют обновление
до подготовки файлов. Успех preflight без локального target commit не доказывает
отсутствия таких коллизий: они обязательно проверяются после fetch.

Перед checkout только проверенные изменённые tracked output копируются в
отдельный приватный каталог `../tmp/service2-static-*`, и копия сверяется.
Затем только эти пути восстанавливаются к HEAD для переключения Git. Сохранённые
байты возвращаются после checkout, включая его ошибку. Если тип пути или symlink
мешает безопасному восстановлению, deployment останавливается, а копия
сохраняется для восстановления. Untracked output не удаляются. Резервная копия
остаётся вне checkout. Это копия статики, не backup БД
и не обещание атомарного deployment или rollback миграций.

Не применять `git reset --hard`, `git clean` или широкие исключения
`public_static/` и `backups/` для обхода этой проверки.

`ADVISOR_MCP_TEST_ENABLED` workflow устанавливает в `false` только в CI.
Deployment не меняет production `.env`; тестовый MCP нельзя включать в рамках
этой настройки.

Если GitHub не создал push-run после уже проверенного merge в `main`,
`workflow_dispatch` для `ci-deploy.yml` используется только как recovery-путь:
в Actions выбирается именно `main`, а в обязательное поле вводится полный
40-символьный SHA текущего `main`. После тестов workflow продолжает deployment
только если ref — `refs/heads/main`, введённый SHA равен
`github.sha`, GitHub API подтверждает, что текущий `main` всё ещё указывает на
этот SHA. Перед exact checkout и SSH проверка `main` через GitHub API
повторяется. Любое несовпадение останавливает pipeline до exact checkout, SSH
и фактического развёртывания; запуск с другой ветки не получает deployment.
Этот recovery-путь не выполняет push самостоятельно и не позволяет развернуть
SHA, который уже не является текущим `main`; независимое содержательное ревью
остаётся обязательным. Отдельный `hosting-connection-check.yml`
выполняет описанную выше проверку подключения.

Deployment не является атомарным и автоматический rollback после применённой
миграции не обещается. Ошибка останавливает последующие шаги, но уже применённая
миграция или установленная зависимость может остаться. Для рискованных миграций
до merge обязателен проверенный backup рабочей БД и отдельный план roll-forward;
возврат к старому коду допустим только после проверки совместимости схемы.

## Автоматическая проверка статусов объявлений Avito

Единственный регулярный планировщик — CronTab существующего hosting-аккаунта.
[Beget поддерживает произвольные команды и Bash-задания](https://beget.com/ru/kb/manual/crontab).
`.github/workflows/avito-status-monitor.yml` сохраняет только ручной
`workflow_dispatch` из `main`: регулярный GitHub schedule удалён. Перед первой
активацией необходимо убедиться, что старые scheduled Actions runs не остались
queued/running. Открытый чат и компьютер владельца не нужны. Используются
существующие hosting-ресурсы и deployment SSH credentials, без нового API,
ключей, OAuth scope, платной подписки или расширения доступа.

`scripts/avito_monitor_cron.py` устанавливает одну помеченную запись в cron
того же пользователя, от которого выполняется protected deployment. Сигнал
подаётся в минуты `7,22,37,52` каждого часа по времени host cron. Время запуска
процесса и безопасная диагностика используют UTC. Это технический 15-минутный
сигнал: приложение выбирает включённые подписки с наступившим `next_due_at`,
сохраняя часовую сетку успешных проверок и ограниченные повторы ошибок.
Глобальные `PATH`, `SHELL`, `MAILTO`, `CRON_TZ` и другие чужие настройки cron
не изменяются. Команда имеет собственные минимальные PATH/HOME/TZ/LC_ALL,
абсолютный virtualenv Python и путь к фиксированному wrapper.

Обычный защищённый deployment **не устанавливает cron** и не требует наличия
CLI `crontab` или свежего внешнего tick. После exact-SHA checkout/migrations
проверяется только существующий bounded `--status`: совместимость runtime,
схемы и агрегатов. Это не вызывает Avito, не создаёт подтверждение tick и
не активирует подписки. Отсутствие/сбой внешнего расписания не блокирует
исправление приложения или посторонний выпуск Service2.

Настройка расписания — отдельное явное действие. На текущем Beget-хостинге
read-only preflight подтвердил `crontab_unavailable`; поэтому используется
документированная панель CronTab, а не обход отсутствующей SSH-команды.
В авторизованных настройках Авито показывается точная shell-quoted команда,
вычисленная из runtime-путей установленного приложения: fixed `tick`, нужный
virtualenv, HOME/PATH/TZ/LC_ALL, подавление вывода. Реальные пути не записываются
в Git или публичные logs. В панели задаётся одно задание на минуты 7,22,37,52;
остальные задания/параметры не изменяются. Само отображение команды не является
регистрацией, а deploy/readiness не записывает успешный tick.

В окружении, где поддержан `crontab`, остаются **явные** CLI-команды `preflight`,
`install` и `remove` для отдельного согласованного setup/rollback. Установщик
сохраняет прежние ограничения: exact SHA, GitHub schedule отсутствует, чистое
окружение, отдельные locks, отказ при занятом worker, проверенная marker-группа,
приватный backup, сравнение непосредственно перед записью и точный readback.
Чужие строки/комментарии/settings сохраняются без изменений. Дубликаты,
изменённые/неуправляемые monitor-строки, управляющие символы/процент в путях,
отказ доступа или неоднозначный ответ CLI останавливают эту setup-команду.
Автоматического перехода на иной scheduler или новых credentials нет.

У crontab нет универсального atomic compare-and-swap. Сравнение до записи и
проверка после неё выявляют изменения, но не заменяют координацию с параллельным
редактированием через панель Beget. При readback-конфликте скрипт останавливается
и не восстанавливает старую таблицу поверх новых чужих заданий.

Cron запускает режим `tick`, который повторно использует
`scripts/run_avito_status_monitor.sh`. Отдельный mutex cron tick, существующий
`service2-avito-status-monitor.lock` и shared `service2-deploy.lock` предотвращают
наложение scans и работу во время замены checkout. Приложение получает
`--limit 10 --budget-seconds 1500`; wrapper ограничен 30 минутами с 30-секундным
TERM grace, внешний tick — 1870 секундами с принудительным завершением всей
группы дочерних процессов. Ручной Actions run ограничен 35 минутами.

Полный stdout/stderr scheduled-команды направляется в `/dev/null`; cron email
не отправляется и общие настройки доставки почты не меняются. Каждый tick
атомарно заменяет один приватный `last-tick.json` размером до 1 KiB в
`../tmp/service2-avito-cron/`: только UTC start/end, состояние и exit code.
Каталог имеет mode 0700, файлы 0600; данные не попадают в Git или public_static.
Backup-таблицы также остаются только в этом приватном каталоге. Успешная завершённая запись
может означать отсутствие due задач: фактический scan доказывается timestamp
подписки. Пропуск занятого tick не заменяет запись, а пропуск wrapper из-за
занятого worker/deployment имеет код 75 и не считается успешным запуском.

Успешные preflight/readiness/readback подтверждают регистрацию задания и
готовность приложения, но не факт работы hosting cron daemon. После включения
подписки самим администратором необходимо дождаться реального автоматического
baseline, проверить безопасный tick timestamp и следующий наступивший scan.
При отказе hosting crontab явная setup-команда завершается ошибкой без fallback
на другой scheduler, новые credentials или изменения прав. Исправный crontab не
является гарантией отсутствия hosting outage или превышения лимитов ресурсов.

Для отката через тот же защищённый канал используется режим `remove` с
`--app-dir` и `--expected-sha` текущего проверенного deployment. Он удаляет только
точно совпавшую marker-группу из актуальной таблицы, сохраняя новые чужие записи;
повторное удаление безопасно. `crontab -r` и восстановление полного старого
backup поверх текущей таблицы не используются. Возвращать GitHub schedule можно
только после подтверждённого удаления native job. Откат scheduler не удаляет
подписки, baseline, историю и уведомления Service2.


Service2 считает readiness подтверждённой только по завершённой записи
`AvitoSchedulerHeartbeat` в общей БД: реальный worker tick с exit code 0,
валидными UTC timestamps и возрастом не более 45 минут. Приватный JSON остаётся
локальной диагностикой, а не источником readiness: на хостинге cron и Passenger
могут иметь разные UID и изолированные файловые контексты. Внешний supervisor
держит shared deployment lock для обоих bounded DB-helper вызовов и worker,
записывает running перед worker и finished только после его фактического
завершения. Каждый запуск имеет UUID; позднее завершение старого запуска не
может заменить новый. Ошибка записи/чтения БД не подтверждает готовность,
миграция создаёт пустую таблицу без выдуманного успеха. Старт процесса, `--status`, открытие страницы и deployment не
являются успехом. До такого подтверждения новая подписка/повторное включение
заблокированы. Для уже активной подписки отсутствие/старение/ошибка tick
показываются как degraded health, но подписка, backoff и снимки не изменяются.
Это проверка готовности; реальную автоматическую обработку объявлений отдельно
доказывает успешный полный baseline и время scan. Отказ API не подменяет статус.
