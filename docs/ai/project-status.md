# Проверенное состояние service2

## 9 сентября 2026: типизированные карточки документов валовой прибыли

По GET-only диагностике регистра продаж подтверждены поля `Recorder_Type` и
`Документ_Type`, номера/даты разрешённых документов и связь расходной накладной
с заказом. Неразрешённые ссылки заказа не используются для группировки. Для
розницы подтверждено отсутствие явной ссылки чек → отчёт и уникальность отчёта
по организации/дате на проверенных сентябрьских датах.

В подготовленном коде OData snapshot v2 сохраняет явный organization-bound
`document_group_key` и русскую подпись документа. Обычные движения группируются
по регистратору; чек присоединяется только к единственному разрешённому отчёту
той же организации и календарной даты. Неоднозначность сохраняет отдельные
карточки. XLSX и прежние строки имеют fallback по старому `document_name`.
Presentation-only объединение точной пары revenue/cost разрешено только для
полной metadata нового OData-контракта и не меняет строки БД или финансовые
итоги; XLSX и старый OData не схлопываются. Snapshot validator сверяет self-group
с первичным документом, retail display — с target-report, а календарную дату
`period` — с `source_date`. На мобильном внутренние строки документа показаны
вертикальными карточками без широкой таблицы; desktop-таблица не изменена.

После независимого ревью усилены self-group и cross-row retail-проверки, а
presentation-collapse ограничен полной v2 OData metadata. Повторный целевой
прогон двух затронутых suites: 62 теста, все прошли.

Миграций нет. В итоговый целевой набор вошли 224 теста reader/draft/dashboard,
unified/daily/auto-apply, диагностики документов и active-period; один тест
штатно пропущен. Две несовместимые synthetic fixtures общего auto-apply были
исправлены и их сценарии повторно прошли. Django checks, отсутствие новых
миграций и `git diff --check` подтверждены. Изменения не публиковались,
PR/deployment и запись в рабочую БД/1С не выполнялись. Контракт:
`docs/1c-profit-document-source-contract.md`.

  рабочей БД не предпринималось, команды миграции/импорта не запускались.
- Публичный адрес из старого отчёта был проверен только неавторизованным HTTP
  запросом. Сетевой proxy окружения отклонил CONNECT с 403, поэтому доступность
  production, страницы входа и отчётов снаружи **не подтверждена и не
  опровергнута**.
- Без учётной записи и рабочей сессии не проверены наличие конкретной
  организации, дата последнего импорта, полнота периодов и контрольные суммы.
- Подключённых MCP resources/templates, browser tool или service2 connector нет.
  Поэтому чат сейчас не имеет машинного канала к отчётам независимо от ролей.
- Локально подготовлен `/mcp/test/` с одним нефинансовым инструментом и без
  обращений к БД. Он проверен Django tests и локальным HTTP-вызовом, но не
  опубликован, не развёрнут и не вызывался из целевого облачного чата.

## Известно только из старого отчёта

Следующие утверждения сохранены как гипотезы, а не текущие факты:

- исторический production-путь и домен, приведённые только во внешнем handoff;
- применение миграций, перезапуск и успешные smoke-проверки на production для
  какого-либо исторического SHA;
- наличие и полнота реальных данных 1С, в частности ФОТ за август 2026 года;
- ранее обсуждавшиеся дубли документов, отрицательная себестоимость, расхождения
  с заказом клиента, продажи менеджеров и прогноз зимы;
- любые исторические разрешения `push`, `merge` или `deploy`: они могли быть
  выданы для отдельных обсуждений, но их точная область не восстановлена.

## Область разрешений этой передачи

Текущая задача разрешала чтение кода и Git-истории, безопасные локальные
проверки, документирование и подготовку предложения read-only доступа. Она не
разрешала бизнес-правки, импорт 1С, доступ/изменение рабочей базы или deployment.
Эти ограничения относятся к данной задаче и не заменяют отдельные разрешения
для будущих точно определённых операций универсальным разрешением или запретом.

## Автоматизация публикации — подготовлено в коде

`development-codex.yml` публикует PR и явно запускает CI для созданного
`GITHUB_TOKEN` head. Серверный poller после независимого AI review готов
публиковать approval отдельной GitHub identity и включать auto-merge точного
head. Push/merge/deployment этой копией не выполнялись; работа на GitHub и
hosting остаётся неподтверждённой до настройки credentials и первого прогона.

Подтверждённый вход штатного цикла — карточка `DevelopmentTask` в service2.
Сообщение из этого Codex-чата само такую карточку не создаёт: в среде чата нет
подключённого service2 tool/API. Поэтому задачи, выполняемые непосредственно в
этом чате, ведущий публикует штатным PR-механизмом Codex, но подключение их к
production poller без отдельного ingress пока не утверждается.

Проверка PR №87 из текущей среды также заблокирована: remote и GitHub CLI auth
отсутствуют, HTTPS получает CONNECT 403. Локальный HEAD `66fcfe5` подготовлен
для обновления существующего PR через кнопку Codex **Update PR**, но актуальные
base/head и состав файлов PR внешним вызовом не подтверждены. Подробный
fail-closed порядок записан в `docs/ai/codex-direct-flow.md`.
