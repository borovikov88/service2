# CRM: перенос данных и матрица прав

Часть [этапа 0](crm-stage-0.md). База сверки:
`3416f0038556c2b6f0bf58c93eadb77541bde350`; требования — [ТЗ 0.4](crm-spec-v0.4.md).
Ни одна миграция, выдача прав или рабочий импорт этим документом не выполнены.

## 1. Перенос: expand → backfill → verify → switch

### 1.1. Инвентаризация перед изменением рабочих данных

Отдельная read-only команда с обязательной организацией и режимом dry-run
выдаёт только агрегаты и технические ID в защищённый отчёт. В Git не попадают
контакты, тексты, файлы клиентов, суммы рабочих договоров или source payload.
Собрать:

- Количество CrmItem по direction/stage/archive reason; неизвестные значения,
  отсутствующие organization/client, ссылки на другую организацию, неактивные
  ответственные. Сверка Client/Pool/ClientOwnedObject и объединённых карточек.
- Задачи/фото на коммерческих CrmItem; supply-задачи и дубли по WaterReading,
  включая архивные; источники приватности, доступные авторы/даты.
- Количество КП, версий, коммуникаций и финансовых batch/snapshot; явные связи
  и доступные устойчивые ключи. Совпадения названий не считать связями.
- Для обслуживания: реальные подтверждённые договоры, редакции/объекты/месяцы,
  незавершённые выдачи и неоформленные поставки из бумажного журнала. Отдельно
  пометить то, что требует документальной проверки сотрудником.
- Реальный размер таблиц/индексов, версия MySQL, длительность блокировок и
  доступное окно переключения. Измерить baseline списка/карточки на стенде.

Пока эти чтения не сделаны, неизвестны количества и доля автоматического переноса.
Снимок Git не даёт права выдумать их или использовать SQLite-фикстуры как рабочие.

### 1.2. Технический журнал переноса

`CrmMigrationRun`: организация, версия mapper, исходный SHA/дата отсечения,
режим, high-water cursor, состояние, агрегаты. `CrmLegacyMap`:
`(organization, source_type, source_id, target_kind)` unique, target FK,
source_fingerprint, run, result/error. Отдельные target_kind=deal/execution/
need/issue сохраняют происхождение и не означают несколько продаж.

Backfill выполняется управляемой management command, пакетами с короткими
транзакциями и возобновляемым курсором. Создание target и map — атомарно.
Повтор без изменений создаёт 0 объектов; изменение source fingerprint до
переключения обрабатывается явно/отправляется на разбор. После ручной правки
target никакой повтор не перетирает её. Схемные Django migrations создают только
совместимые структуры; длинный рабочий backfill не запускается внутри deploy.

archive reason, старый ID/URL и признак legacy. Указанное ниже состояние

не становится активной из-за неизвестного результата. Неархивные неизвестные
результаты видны в очереди сверки отдельно от точных KPI. `created_at` и другие
достоверные даты сохраняются как исходные; дата переноса — отдельное поле.
История стадий до миграции неизвестна, событие migration не выдаётся за историю
переходов. Неизвестная валюта/смысл legacy amount требуют проверки; сумма не
становится принятым заказом или выручкой автоматически.

| Данные | Правило переноса и сверки |
| --- | --- |
| Clients/contacts/company links | ID сохраняются; никакого массового merge по имени/телефону. Общий merge расширяется отдельно с preview, защитой onec_ref и перечислением новых связей |
| Pool/ClientOwnedObject | Не клонировать объекты. Будущие объекты не активировать; legacy NULL organization не заполнять первой организацией пользователя |
| ServiceTask | ID/исполнители/приватность/история остаются. Новая коммерческая связь создаётся по legacy map; старый FK служит происхождением до переключения. Legacy sync перестаёт менять замороженный commercial CrmItem |
| Проект исполнения | Один уникальный execution для `prj_hold/prj_done` и доказанных иных случаев; исторический статус помечен reported. Плановые задачи не становятся повторными фактами запуска |
| Фото/файлы | Сохранить storage и ID, дать типизированную связь новой карточке; старый URL проверяет новый scope. Не копировать файлы в Git |
| КП | Существующие версии не меняются. Подтверждённая привязка создаётся явно; одинаковое название не связывает расчёт и сделку |
| Коммуникации | Оригинальные ID/время сохраняются. Исторические события по умолчанию historical; нет массовых новых лидов, ответов или уведомлений |
| Потребности WaterReading | Устойчивая связь с заявкой не зависит от активности задачи. Несколько старых supply-задач — группа разбора, не удаление «лишних» и не новый лид. Повтор той же версии не создаёт заявку; изменение после исполнения — коррекция |
| Договоры обслуживания | Только подтверждённый состав периодов/объектов/условий. Поля Pool и money plan — кандидаты, не доказательство юридического договора |
| Бумажный журнал | Перенос открытых строк с source namespace+проверяемым номером страницы/строки и import key. Нет устойчивого ключа — явное назначение оператором до записи. Выдача без подтверждения не становится доставкой |
| Текстовые материалы старых визитов | Сохранить текст; количества, упаковки, цены и доставку не извлекать как подтверждённые факты без проверки |
| Финансовые ссылки | GUID + namespace + тип + scope, версия и полнота. Не переносить суммы в новые финансовые проводки. Исчезнувшая/изменённая строка активной версии обнуляет достоверность распределения, не историю |

### 1.5. Переключение и восстановление

1. Сделать штатный backup БД/необходимых media и доказать restore на отдельном
   стенде. Определить владельца запуска, объём, пороги блокировок и stop-критерии.
2. Deploy совместимой схемы/кода под выключенными флагами; существующий путь
   работает. Новые таблицы не требуют destructive migration или смены PK.
3. Dry-run и пробный backfill на копии, затем повтор и возобновление после сбоя.
   Подтвердить сверки ниже; разрешённый рабочий перенос — отдельный запуск.
4. Shadow-read сравнивает старую коммерческую выборку и новые карточки без
   двойной записи. Пока legacy writable, изменённые после cursor записи повторно
   сверяются по fingerprint. Перед финальным delta на короткое окно блокируются
   legacy commercial writes; приём коммуникаций продолжает надёжно сохраняться.
5. В одной контролируемой операции для организации переключить canonical reader
   и writer на v2. Старые URL ведут на новую карточку/историческое представление;
   old POST/API/bulk/admin не остаются вторым способом правки. Service CrmItem
   продолжает работать. Пилот и критерии расширения перечислены в PR-14/30.
6. При ошибке отключить новые изменяющие действия, сохранить очередь событий и
   уже созданные v2-данные, показать режим обслуживания. После первой v2-записи
   нельзя просто включить legacy writer: он не содержит новых фактов. Нужны
   совместимый предыдущий релиз, fix-forward либо проверенный отдельный план
   обратного переноса. Rollback кода не обещает rollback MySQL DDL/данных.
7. Полный restore — аварийная операция с остановкой записей и последующим
   воспроизведением принятых после backup событий по ключам; не штатное
   «откатить без потерь». Удаление legacy-таблиц/полей — поздняя отдельная задача.

Флаги по организации: `crm_v2_read`, `crm_v2_write`, `crm_intake_process`,
`crm_materials`, `crm_accounting`, `crm_close`, `tender_mail`, `tender_autoselect`.
Отключение processing не отключает сохранение входящих. Последний флаг остаётся
выключен до Q13. Код и воркер валидируют допустимые комбинации флагов.

Обязательные сверки: source count = mapped + review + явно исключённые;
одна source commercial record → один deal; нет cross-org ссылок; прежние ID
доступны; суммы исходных полей сверены по типу/валюте без придания нового смысла;
private visibility сохранена; остатки количеств неотрицательны; распределения
не превышают источники; активные версии не суммируются с заменёнными. Число
неразобранных записей видно и утверждается для пилота, не скрывается как успех.

## 2. Права: подтверждённые границы и предлагаемые capabilities

Текущий `OrganizationAccess`: owner/admin/manager/service/installer/accountant.
Отдельной роли «кассир» нет. Внешний бухгалтер/советник не получает роль accountant
как универсальный read-only доступ. Существующие финансовые и коммуникационные
capabilities сохраняются; новая CRM не расширяет их по факту связи с карточкой.

Предлагается `CrmAccess(organization, user)` unique с отдельными действиями и
при необходимости scope воронок. Проверка: активный пользователь + доступ к
конкретной Organization + capability + scope записи/источника. Для менеджеров
D06 гарантирует командный просмотр сделок данной организации, а не только «мои».
Финансовые поля, private-источники и файлы фильтруются дополнительно.

Обозначения матрицы: **Д** — подтверждено D-решением; **П** — предложенное
назначение для реализации; **К** — только отдельно выданная capability/действующее
право; **—** — не выдаётся по этой роли. Предложения не являются уже выданными
правами. Неопределённые Q06-права по умолчанию выключены до решения перед запуском.

Александра в организации, не сравнением строк имени и не всем owner/admin.
В этом пакете ID не угадывается и право не выдаётся. Штатный superuser остаётся
техническим механизмом проекта; он не заменяет бизнес-настройку D08.

Текущий `services/finance.py` разрешает управленческий контур owner/admin/accountant,
а manager имеет отдельные операционные возможности. Для CRM-расчётов нужно
разделить просмотр разрешённого статуса расчёта и просмотр сумм/маржи. Если
существующая capability не допускает поля, поле отсутствует во всём ответе,
а не скрывается CSS. Проверка готовности закрытия может выполняться внутренним
сервисом без раскрытия пользователю защищённых чисел; новый разрешённый статус
согласуется в Q06. Личные зарплаты в CRM не включаются.

### 2.1. Приватность потребностей и производных данных

D04 требует видимости рабочей потребности, но не открывает всю private-задачу.
Новые `CrmServiceNeed` могут публиковать только согласованный whitelist: объект,
требуемый состав, автор, дата, состояние. До решения Q06 источники наследуют
текущую приватность; командная публикация выключена. Это временно ограничивает
AC39 и не выдаётся за завершённую общекомандную очередь потребностей.

После настройки публикация хранит автора/версию/основание и права отдельно от
комментариев задачи. Старые private-задачи не становятся public массово.
Изменение source privacy немедленно ограничивает превью/поиск/AI-резюме/экспорты;
кэш и поисковый индекс инвалидируются, повторная авторизация обязательна при
чтении. Уведомление несёт минимум безопасных полей и защищённую ссылку; уже
доставленное уведомление невозможно «отозвать», поэтому private-текст в него
не включается. Исторический аудит также не становится обходом доступа.

### 2.2. Проверки прав перед включением

Негативная матрица охватывает HTML/partial/канбан, POST/API, bulk, lookup, admin,
поиск, экспорт, вложения, фоновые jobs и уведомления. Проверять service в A +
manager в B; чужие ID в каждом FK; деактивированного пользователя; изменение
роли/приватности во время операции; просмотр сделки с недоступным источником;
запрет изменения чужой записи при командном чтении; повтор ранее разрешённой
команды после отзыва права. Новый endpoint не считается защищённым по меню.

## 3. Отдельное независимое ревью

Это план будущих проверок, не заявление о выполненном независимом ревью пакета.
Для docs-only этапа выполнена самопроверка; AGENTS.md не требует отдельного
агента только ради документации. При реализации проверяющий получает задачу,
приёмку, актуальный final diff/head и самостоятельно проверяет код и тесты.
Если привлекается агент, использовать GPT-6.1 Sol по указанию владельца,
без платного API fallback; обычно один независимый проверяющий достаточен.

| Контроль | Что проверяет отдельный ревьюер | Условие прохождения |
| --- | --- | --- |
| R — права | Org-scoped capability, private/производные поля, IDs/bulk/admin, D06 без расширения финансов, точечный D08 | Негативные security tests и отсутствие незакрытых замечаний; до выдачи прав/включения экрана |
| M — миграции | MySQL DDL/индексы/locks, FK/unique, idempotency/resume, карта стадий, legacy URLs и writer, сверки, backup/restore/rollback | Прогон на копии + повтор/сбой + восстановление; до рабочего backfill/cutover |
| F — финансы | Namespace/seller scope, идентичность строк/версий, валюты/НДС/округление, отсутствие двойных сумм, D02/D10, неизвестность и возвраты | Целевые regression/financial tests, проверенный контракт источников и отсутствие незакрытых замечаний |

R/M/F могут проверяться одним независимым ревьюером, но каждый имеет отдельный
результат и не заменяется общим «LGTM». Изменённый после ревью рискованный diff
проходит повторную проверку. Обязательны Django check, migration check, целевые
тесты и полный CI на точном финальном commit. Для конкурентных/DDL сценариев
дополнительно MySQL. Локальные команды БД используют
`--settings=service_site.test_settings`; CI MySQL — собственные штатные settings.
Далее действующие branch/environment guards, protected deploy, preflight и
health-check. Доступный workflow не доказывает существование всех настроек ruleset.
Миграция рабочих данных, выдача прав и deployment должны входить в следующую
явно поставленную задачу; этот план их не запускает.
