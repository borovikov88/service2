# Канал доступа финансового ИИ-советника

Срез возможностей выполнен **5 сентября 2026 года**. Документ определяет
конкретный минимальный канал; он не утверждает, что этот канал уже реализован
или развёрнут.

## Проверенная цепочка сейчас

| Уровень | Результат проверки |
|---|---|
| Сеть из текущей среды чата | HTTPS proxy отклоняет CONNECT к production-домену с 403 до TLS и Django; прямой DNS недоступен |
| Браузер | Подключённого browser tool, Chrome/Chromium, Playwright или Selenium нет |
| Подключённые инструменты | MCP resources и templates отсутствуют; инструмента service2/БД нет |
| Авторизация service2 | Не начиналась: у агента нет отдельной сессии или credentials; вход владельца на телефоне не передаётся чату |
| Права на отчёты | Проверены только по коду; production-права и реальные отчёты не прочитаны |

Таким образом, существующий HTML-вход и будущая роль внутри Django сами по себе
не создают канал для ИИ. Устранять proxy 403 передачей пароля в чат нельзя.

## Целевой интерфейс: статус проверки

Целевая схема — техническая команда в Codex и отдельный финансовый советник в
Codex. Подключение советника к ChatGPT вместо Codex не выбрано. Доступный в
локальной среде MCP endpoint и его локальные protocol tests не доказывают, что
выбранная среда советника в Codex умеет подключаться к нему или вызывать его.
Способ внешнего подключения Codex к service2 ещё требуется подтвердить
фактическим вызовом из этой среды.

После подтверждения способа доступа рабочая цепочка должна быть следующей:

Цепочка:

`чат советника → авторизованный MCP/app connector → GET advisor API → active
service2 data`.

Коннектор будет хранить отдельный от пользовательского пароля отзываемый service token
в защищённой конфигурации, а не в prompt, Git или файле выгрузки. Если среда
чата не может напрямую обращаться к production-домену, удалённый MCP endpoint
размещается в разрешённой сети и сам обращается к service2. Это отделяет сетевой
доступ от прикладной авторизации и финансовых прав.

## Подготовленный connection probe

В текущем Django-приложении подготовлен stateless JSON-over-HTTP MCP probe
`POST /mcp/test/`. Он не обращается к БД и публикует ровно один инструмент
`service2_connection_test` без аргументов. Ответ явно маркирован как тестовый:

`TEST DATA — service2 connector check; no financial data was read.`

Локальные protocol tests подтверждают `initialize`, `tools/list`, `tools/call`,
валидацию JSON-RPC/media types и отсутствие запроса к БД. Это **не** подтверждает
полную совместимость Streamable HTTP или вызов из целевой среды советника в
Codex: endpoint ещё не опубликован и не развёрнут. По умолчанию probe выключен
environment-флагом; при включении ограничивает размер запроса, проверяет
заданный allowlist Origin и возвращает `Cache-Control: no-store`. Перед
публичным включением требуется rate limit на ingress.

## Планируемые финансовые инструменты после успешного probe

1. `list_finance_organizations` — возвращает только организации, входящие в
   scope токена.
2. `get_monthly_finance` — принимает `month`, непустой список
   `organization_ids`; возвращает строки
   по организациям и сводный итог.
3. `get_finance_data_status` — возвращает активные источники, покрытие месяцев и
   свежесть без запуска refresh/import.

Все инструменты являются чтением. В MCP и API не публикуются методы импорта,
confirm/cancel, refresh/apply, изменения классификаций или финансовых операций.

## API-контракт выбранного месяца

Минимальный внутренний endpoint:

`GET /api/finance/advisor/monthly/?month=YYYY-MM&organization_ids=ID,ID`

Ответ содержит:

- выбранный месяц и применённые фильтры;
- `id` и название каждой организации;
- выручку, аналитическую себестоимость, валовую прибыль, начисленный ФОТ,
  поступления, платежи и чистый денежный поток по каждой организации;
- свод по явно выбранным организациям;
- доступность каждого источника, неполную себестоимость и отсутствующие месяцы;
- источник, идентификатор активной версии и timestamps подтверждения/обновления.

Деньги передаются decimal-строками. Отсутствующие данные возвращаются как
`null` с `available=false`, а не как ноль. Если хотя бы у одной выбранной
организации источник прибыли, ФОТ или ДДС отсутствует, соответствующий
consolidated показатель
имеет `complete=false` и не выдаётся за полный итог. При неопределённой
себестоимости `cost` и зависящая от неё `gross_profit` также имеют
`complete=false` и не дополняются нулём.

## Организации и защита от двойного счёта

- Один пользователь модели может иметь несколько `OrganizationAccess`.
  Случайный выбор через существующий `organization_for_user().first()` для API
  не используется.
- Токен принадлежит отдельному service principal. Его server-side scope —
  единственный источник полномочий advisor API и хранится как уникальные связи
  principal–organization. Обычный `OrganizationAccess` и роль `finance_viewer`
  в минимальном машинном канале не используются.
- Scope токена содержит разрешённое множество организаций. Каждый запрошенный
  ID проверяется сервером; наличие хотя бы одного чужого ID отклоняет весь
  запрос.
- Список scope строится с `distinct()`, а финансовые строки не соединяются с
  таблицей полномочий: разрешения не должны умножать суммы.
- Для каждой организации используются только активные версии по ключу
  `(organization, report_type, period_month)` и штатные `active_for()` querysets.
- Сначала формируются итоги каждой организации, затем складываются денежные
  значения. Рентабельность пересчитывается из сводной прибыли и выручки, а не
  складывается или усредняется.
- Свод всегда возвращает состав организаций. Модель не умеет автоматически
  распознавать одну и ту же базу 1С, загруженную в две организации, поэтому
  объединять можно только явно запрошенный владельцем набор. Ограничения одной
  организацией нет.

## Следующая проверка подключения

Сначала техническая команда должна установить поддерживаемый способ внешнего
подключения именно для выбранной среды финансового советника в Codex. Если это
невозможно проверить без действия владельца в интерфейсе его аккаунта, ведущий
запрашивает только это конкретное действие после завершения доступных ему
проверок. Проверка настроек ChatGPT для этого не требуется и выбором ChatGPT не
считается.

## Размещение и точный блокер

Минимальный probe размещается внутри существующего Django/Passenger-приложения
на том же HTTPS-домене; отдельный сервер для него не нужен. Локальный ingress,
hosting credentials и подтверждённая команда deployment отсутствуют. Proxy
блокирует GitHub и production с CONNECT 403, прямой DNS недоступен, поэтому
ветку нельзя push, endpoint нельзя развернуть и реальный вызов из Codex сейчас
выполнить невозможно. После проверки возможностей целевой среды потребуется
восстановить штатный путь публикации и deployment; его нельзя подменять
локальным MCP-тестом.

## Критерий приёмки канала

В новой сессии советник без файлов и скриншотов владельца вызывает инструмент
для выбранного месяца и самостоятельно показывает выручку, себестоимость,
валовую прибыль, ФОТ, состав организаций, фильтры и свежесть. Пропуски отмечены
явно. Аудит БД подтверждает, что чтение не создаёт import/sync runs и не меняет
финансовые сущности.
