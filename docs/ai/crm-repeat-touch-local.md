# Подтверждённое продолжение потребности — локальный срез

Основание: CRM_Aqualine_TZ_v0_4.md v3, §5–6, AC01–04/09/21–23/28/34.
База: main 4a4b8a7864356a0f1088e3e89f4d26a384355cc0. Без миграций.

## Контракт

Используется существующая команда `lead.transition` с результатом `duplicate`
и явным `target_lead_id`; отдельной параллельной модели объединения нет.
В интерфейсе результат назван «Продолжение существующей потребности».
Менеджер сначала подтверждает смысл обращения и выбирает свою активную
независимую потребность. По телефону, имени или новизне сделки выбор не делается.
Неоднозначность остаётся на ручном разборе, без автоматического назначения.

Команда закрывает исходный лид, отменяет его открытый следующий шаг по
существующему правилу и сохраняет его историю. Источники не перемещаются и
не копируются. Подтверждённые указатели диалогов переводятся на целевой лид:
последующие сообщения/ревизии того же контекста поступают туда. Целевая карточка
получает признак необходимости разбора, новую revision и событие аудита;
ответственный, её задача, сделки и финансовые факты не изменяются.

История целевого лида включает доступные источники непосредственно связанных
исходных карточек. Две SQL-проекции ограничены по получателю до передачи в UI;
совместное присутствие обеих карточек на странице не меняет историю.
Проверка contributors выполняется keyset-порциями по 200 ID, отдельно от
оконного запроса источников: вложение обеих privacy-проверок вызывало
`parser stack overflow` на SQLite 3.45. Размер порции не ограничивает историю.
Top-K объединяется глобально по каждой карточке; после разделённых чтений права
contributor проверяются снова. Это не атомарный снимок: при отзыве прав страница
может безопасно недобрать элементы, а стоимость обхода растёт с числом contributors.
Пагинация использует существующий подписанный курсор и стабильную пару
received_at/source ID. Приватность и права каждого источника проверяются заново,
в том числе перед запросом существующего AI workflow. GET не запускает анализ.

Транзакция и mutex организации сериализуют intake и ручное подтверждение.
Существующие operation key/revision защищают повтор и устаревшую карточку.
Повтор сохранённой команды после закрытия target возвращает прежний результат
при актуальных правах, без повторного переноса контекста и событий аудита.

## Границы

- Другие новые звонки с новым provider call ID не считаются автоматически той
  же потребностью. Такой контекст требует подтверждения человеком.
- Связь с существующей сделкой использует прежний `linked`/CrmLeadDealLink.
  Не добавлены подбор по телефону или автоматическое закрытие сделки.
- Источники исторических duplicate-карточек доступны через прежнюю явную связь;
  их thread автоматически не переписывается и массового backfill нет.
- Новое подтверждение цепочек, origin_lead и переноса лидов с дочерними дублями
  блокируется: нужен отдельный сценарий разбора, чтобы не переопределить
  ранее подтверждённые связи. Между владельцами автоматической передачи нет.
- Права, cutoff, owner privacy, внутренние/исходящие звонки и scheduler не меняются.
- Native MySQL и закреплённый CI Chromium должны быть проверены перед выпуском;
  локальный SQLite не доказывает поведение блокировок MySQL.

## Проверки

Синтетические тесты: сохранность источников и задач; маршрутизация продолжения;
новая независимая потребность; обе карточки на одной странице; cursor без
пересечения; отзыв прав и приватный contributor при доступном target; запрет AI;
запрет изменения чужого target; replay после закрытия; native SQL races повторной
команды и конкурентного закрытия target. Chromium: явный выбор, отмена без POST,
подтверждение, переход по связи и reload, desktop/mobile.

Публикация этого пакета, PR, CI на GitHub, merge/deploy и живые данные не входят
в локальное разрешение. Intake ops остаются отдельным незакрытым вопросом.
