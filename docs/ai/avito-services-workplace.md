## Этап 1. Надёжность существующего источника

Проверяемый первый выпуск:
- После перехода одного из 11 объявлений в неактивное состояние допустимые
  правки оставшихся активных проходят. Неактивные строки сохраняются в черновике
  и истории; их исключение из нового XML явно отображается, повторная
  активация не выполняется как побочный эффект публикации.
- Проверены принадлежность аккаунту, полнота покрытия всех активных,
  неизменность связки Id/AvitoId, запрет случайного исчезновения известных Id,
  оптимистическая блокировка и повторная проверка области при сохранении.
- Новые импорт, правка и публикация принимают максимум 10 фотографий.
  Существовавший опубликованный снимок не обрезается и не ломается только
  из-за изменения ограничения; превышение требует отдельной новой правки.
- Сохраняются версии и изменения по полям, автор, причина и время.
  Восстановление создаёт новый черновик, не меняет опубликованный файл само.
- Публикация XML и наблюдение статуса у провайдера не считаются доказательством
  применения текста/фотографий. API item detail их не возвращает.

Оставшиеся обязательные части этапа 1:
проверка доступности/формата фото с SSRF-защитой и безопасная загрузка файлов;
подтверждение цепочки конкретная версия → фактически забранный файл → upload
→ результат строки; автоматическое наблюдение сроков и корректное различение
обычного истечения, ручного снятия, отклонения, блокировки и неизвестной причины.
Существующий status old не доказывает причину без других данных.

Возобновление с сохранением Id и AvitoId разрешено только при подтверждённой
нулевой дополнительной стоимости и понятных последствиях автозагрузки.
ListingFee=Package, положительный баланс или истечение примерно 30 дней сами
по себе не подтверждают бесплатность. Неизвестная стоимость блокирует действие,
платная требует согласования. Копии вместо восстановления запрещены.
Массовую принудительную загрузку для одного объявления не выполнять без проверки
последствий для остальных. Проверка active перед публикацией не гарантирует active
в момент последующего забора файла Авито. Семантика DateEnd и условная бесплатная
реактивация для услуг не подтверждены доступной первичной документацией; новое
поле DateEnd как предполагаемая защита не добавляется. Это ограничение проверки,
а не гарантия отсутствия повторного размещения между двумя наблюдениями.

## Этап 2. Новые объявления и отдельный доступ Авито

Создание с постоянным внутренним Id до первой публикации; AvitoId — только после

город/адрес, заголовок/описание, цена/прайс, обязательные характеристики,
разрешённые контакты, фотографии, предпросмотр. Дубли проверять с учётом города.
Фото: реальные файлы и ссылки, превью/обложка/порядок, формат и доступность,
максимум 10 до публикации. Мобильная и тёмная темы.

Отдельный Avito API/MCP resource со своими audience/scope и серверной проверкой
connection/account/organization. Разделить чтение, черновики и разрешённые

остаются на сервере. Новый платный LLM/API/сервис без согласования не подключать.

## Этап 3. История аналитики, обращения и контроль

Ежедневные account/item snapshots, backfill пропущенных полных дней,
уникальные ключи и идемпотентный повтор. Периоды: последние 7 полных дней,
предыдущие 7 и 30 полных дней Asia/Barnaul. Показы/просмотры/обращения с
доступной разбивкой/избранное/расходы/размещение/продвижение, источник и свежесть,
неполный охват. Missing не равен zero. Проверять денежные единицы и проценты,
не складывать пересекающиеся счётчики в уникальных людей. CTR, конверсия и CPA
только с подходящими числителем/знаменателем; предупреждения учитывают объём.

Webhook: подтвердить регистрацию и реальную доставку, добавить надёжный
cursor/pagination backfill вместо нынешнего ручного bounded чтения.
Контроль неотвеченных и времени ответа, явный неопределённый исход отправки.
Вложения отправлять только поддержанным механизмом провайдера, не считать
локальную загрузку доставкой. Автоответы не включать; допустимы черновики.

Связь объявление → обращение → клиент → КП → заказ → выручка/валовая прибыль
только по подтверждённым идентификаторам и существующим CRM/финансовым
механизмам. Неизвестную связь показывать, поддержать подтверждённую ручную
привязку. Не изменять 1С и не вводить отдельный расчёт прибыли.

Проверки аккаунта в 08:00, 12:00, 16:00, 20:00 Asia/Barnaul. Тихие часы
распространяются на повторные попытки: ночные находки в следующий дневной отчёт.
Утром короткий отчёт даже без проблем; по понедельникам расширенный.
Контролировать раздельно аванс/кошелёк/бонусы, XML, autoload, статусы/сроки,
доступ API и живость worker. Worker может тикать чаще без лишних provider reads.
Freshness account snapshot считать по четырём слотам и задержке, heartbeat
worker отдельно. Расписание забора файла Авито отдельно от уведомлений.
Срок тарифа — подтверждённый источник; существующий ручной ввод с явной
пометкой остаётся резервом. Одинаковые неизменившиеся проблемы не повторять.

## Этап 4. Продвижение, спрос и эксперименты

Актуальные provider offers/prices для конкретного объявления → предложение
(услуга/срок/стоимость/цель) → согласование → поддержанный API → проверка услуги
и фактического списания → оценка результата. Лимиты на объявление, аккаунт,
день и месяц; транзакционная защита от конкуренции и двойной покупки.
Timeout не означает отсутствия покупки: сначала сверить результат.
Реальные тестовые покупки без отдельного разрешения запрещены.

База спроса: фраза/намерение/регион/период/дата/источник/связанные объявления;
Wordstat и доступные официальные данные Авито раздельно, импорт выгрузок.
Не придумывать частотности и не складывать пересекающиеся широкие запросы.
Эксперимент: гипотеза, одна основная переменная, старт/база/срок/результат.
Рекомендация: объявление, основание, конкретная правка, метрика, дата проверки.
Новые тексты не придумывают цены, гарантии, опыт и возможности компании.

## Приёмка каждого выпуска

Целевые regression/security tests, Django check и migration-state check по риску;
независимый reviewer для изоляции/прав/миграций/опасных действий. Затем зелёный
CI точного head, штатный merge, exact-SHA deploy/preflight и health.
Provider mutations проверять безопасными подменами; реальные проверки начинать
с чтения. Отчёт о сдаче разделяет код, production enablement, проверенный
provider result, ограничения и конкретные необходимые действия владельца.
