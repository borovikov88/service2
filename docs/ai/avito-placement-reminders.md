# Напоминания о сроках размещения Услуг

Область: только connection_id=4 / account_id=446312402. Напоминания работают
в существующем `monitor_avito_statuses`, отдельного расписания, коллектора или
миграции нет. Требуется уже включённая self-subscription `AvitoStatusMonitor`;
получатель — только её действующий владелец/администратор с сохранёнными правами
`subscriber_allowed`. Доступ других сотрудников не становится подпиской.

В существующем согласованном окне 08:00–21:00 Asia/Barnaul worker проверяет
сохранённые owned observations. При возрасте проверки от 12 часов использует
существующий `verify_owned_observations`: внешнее чтение вне row locks, штатные
проверки actor/account/org/credentials/revision/draft и повторная проверка
подписки до сохранения. Используется общий item_detail throttle. При остатке
общего бюджета менее 60 секунд новое чтение не начинается. Сохраняется обычная
append-only verify-запись; draft/published/revision, feed URL и контент не меняются.
При provider-ошибке tick получает частичную ошибку, старые данные не затираются.
Независимая локальная доставка продолжает использовать пригодные данные до 24
часов; ошибка refresh возвращает outcome=failed с фактическим числом созданных
уведомлений, штатный worker завершается кодом 2. Сами тексты ошибок не сохраняются.
Вне окна 08:00–21:00 новые проверки не начинаются. Уже начатая проверка может
завершиться после 21:00; перед каждым in-app уведомлением окно проверяется снова.
Следующий дневной tick догоняет актуальный порог. Реальная периодичность зависит
от работающего native worker.

Для доставки нужны точное совпадение Id/AvitoId с черновиком, доверенный
`avito_item_detail` и возраст сохранённой проверки и отдельного наблюдения не
более 24 часов. Данные из будущего не принимаются. Статус должен быть active;
более новый неактивный snapshot монитора и owner_withdrawn блокируют напоминание.
Отсутствие, недоверенный источник и повреждённое значение не означают ноль или
окончание срока. Источник календарной даты — только сохранённое finish_evidence
с соответствующим finish_state/source. Дата без времени/зоны остаётся такой;
срок с подтверждённым offset отображается календарной датой по Барнаулу.

Пороги: 7, 3 и 1 календарный день. Первый запуск в интервале 4–7 дней отправляет
только 7, в интервале 2–3 — только 3, за день — только 1. Более поздние 3/1
приходят отдельно. В дату источника догоняется только пропущенный порог 1;
отдельного due-события нет. После неё сообщение не создаётся, истечение/архив
не выводятся из даты. Изменение срока или сохранённый
подтверждённый цикл размещения создают новую generation; обычное обновление того
же срока её сохраняет. Состояние generation/stage и Notification сохраняются
в одной транзакции с row lock подключения. Уникальный dedupe_key дополнительно
защищает повторную доставку. Временное отсутствие строки в черновике не удаляет
её generation/stages. Память ограничена 1000 известными AvitoId (пять полных
поддерживаемых наборов по 200); достигнув лимита, новые Id пропускаются с
outcome=failed/capacity_exhausted вместо удаления прежней дедупликации. Нужна
диагностика роста набора, а не автоматическое вытеснение истории выдач.
Отключённые in-app notifications не расходуют порог.

Доставка только в Service2 через `notify_users(send_push=False)`. Нет push,
клиентских сообщений, email, SMS, платежей или повторного размещения.
Технический итог tick: `AVITO_PLACEMENT_REMINDER outcome=... notifications=...`;
это число созданных in-app записей, а не доказательство прочтения получателем.

## Read-only доказательство выполнения

`placement_reminder` входит в общий `avito_runtime.checks` только для
connection4/account446312402. Штатный worker передаёт observer с реальным
`worker_context()` run_id; запись разрешена только активному supervisor run,
с проверкой исходного account/org/channel binding. UI и существующий
`get_avito_diagnostics` читают эту же scoped projection, без нового tool/scope.
Незавершённый, чужой или сменивший binding запуск не подтверждает результат.

В настройках подключения `/communications/connections/4/edit/`, раздел
«Фоновые проверки этого подключения», видны источник
`saved_owned_avito_item_detail`, configured/enabled и текущее окно
08:00–21:00 Asia/Barnaul отдельно от outcome, времени и фиксированного кода
последней завершённой проверки. Доказательство старше штатных 45 минут явно
помечается старым; время чтения страницы/MCP не заменяет время проверки.
Счётчик `last_worker_notification_count` означает только реально созданные
in-app записи; отсутствие доказательства/исключение даёт unknown (`null`),
а не 0. Доставка и прочтение из этого счётчика не следуют.

Ночной результат `skipped/quiet_hours/0` записывается без refresh, Notification
и расходования дневного stage. Фиксированные причины включают отсутствие или
отключение subscription, `placement_recipient_unavailable`, `placement_stale`,
`placement_data_invalid`, `placement_refresh_failed`,
`placement_capacity_exhausted`, отключённые in-app preferences, отсутствие
подходящих порогов и уже сохранённые записи. Ошибка refresh может сопровождаться
положительным фактическим счётчиком fallback по пригодным данным до 24 часов.
Обычный scan по-прежнему возвращает `(outcome, count)`; observer добавлен
необязательным keyword-аргументом. Новых настроек, Cron, collector, миграций,
получателей и provider writes нет; connection1 не получает этот check.

## Рабочая проверка после штатного выпуска

1. Read-only проверить область и уже включённую подписку статусов, её recipient
   и текущие права. Не включать подписку от имени другого человека.
2. После первого штатного завершённого native tick открыть под действующим
   владельцем `/communications/connections/4/edit/`, «Фоновые проверки этого
   подключения» → «Напоминания о сроках размещения Услуг». Сверить source,
   outcome, fixed code, исходное время и число записей с общей runtime projection
   в `get_avito_diagnostics(connection_id=4)` (при уже выданном доступе).
   Ночью ожидается `skipped/quiet_hours/0`; до дневного tick это не доказательство
   создания дневных уведомлений. После 08:00 проверить новый timestamp/outcome,
   не переиспользуя ночное или старое доказательство. stdout
   `AVITO_PLACEMENT_REMINDER` и supervisor/exit status остаются дополнительными
   свидетельствами. У owned observations после требуемого refresh должны
   появляться свежие checked_at/last_checked_at без изменения контента.
3. Только для реального существующего объявления с подходящей датой и разрешённым
   получателем проверить in-app запись с `avito-placement:4:` и stage 7/3/1.
   Не менять даты или статус ради теста и не запускать реальные тестовые отправки.
4. Повторный штатный tick не должен создать дубль; следующая фактическая граница
   3/1 должна создать отдельную запись. Если подписка выключена, данные stale,
   источник неизвестен или наступило ночное окно, отсутствие сообщения ожидаемо.

Синтетические regression tests и `manage.py check` не подтверждают production
сбор, доставку или прочтение. Эти факты проверяются отдельно после deployment.
