# Проверки GitHub: выбор и параллельное выполнение

Исполняемые команды находятся в `.github/workflows/ci-deploy.yml` и вызываемом
`.github/workflows/management-finance-mysql.yml`. Правила выбора реализованы в
`.github/scripts/ci_policy.py`, распределение тестов — в `ci_test_runner.py`.
Markdown объясняет эти программы и сам по себе не меняет automation.

## Выбор набора

Workflow запускается на каждом PR/push main. Он читает полный локальный Git diff
по точным SHA события, включая обе стороны переименования. Он не полагается на
ограниченный список файлов GitHub path filters. Неизвестный/недоступный diff,
пустой diff и ручной запуск выбирают полный набор.

| Изменения | Проверки |
| --- | --- |
| Только AGENTS.md/README.md/CONTRIBUTING.md или `.md/.rst/.txt` в docs | Проверки CI policy, workflow и быстрые проверки scripts/JS; без Django/Chromium/MySQL |
| Только известные файлы изолированного tools/aqualine22-calculator, можно вместе с документацией | Быстрые проверки, включая калькулятор и его границы публикации; без Django/Chromium/MySQL |
| Только `.js/.css/.html` в static/pool_service/crm_live, `.html` в templates/pool_service/crm_live или templates/pool_service/avito, можно вместе с документацией | Четыре группы серверных CRM/Avito/общих тестов и все четыре браузерные группы; без MySQL, поскольку серверный SQL-код не менялся |
| Python, модели, миграции, права, финансы, зависимости, общие шаблоны/стили, CI policy, смесь калькулятора и UI или любой неизвестный путь | Полный серверный набор, четыре браузерные группы, полный существующий набор MySQL |

Для UI CRM и Avito объединены из-за истории обращений, атрибуции и доступа.
Неизвестные/новые тестовые модули и старые смешанные модули включаются всегда;
тесты владельца, звонков, задач и организационной изоляции не исключаются.
Выбор по произвольным изменениям бизнес-логики пока не применяется: до доказанной
карты зависимостей для них сохраняется полный набор.

## Параллельность и полнота

Серверный runner использует стандартное Django discovery. Он распределяет классы
по четырём группам детерминированно с учётом их размера и миграционной нагрузки.
Класс и его setUpClass/tearDownClass не разделяются; каждая группа имеет отдельную
одноразовую БД. Проверка multiset идентификаторов не допускает потерь и добавленных
повторов. CI_TEST_INVENTORY выводит количество тестов и hash состава; discovery
может перечислить полный набор на каждом runner, но исполняется только его доля.

Четыре существующие группы Chromium запускаются одновременно с серверными.
В серверных группах браузерные opt-in flags выключены, как в прежнем общем suite.

MySQL workflow вызывается основным workflow и имеет четыре независимых сервиса
MySQL 8.4. `.github/mysql_test_labels.json` сохраняет все 122 различных прежних
label; два повторявшихся label перечислены один раз. Проверки native backup и
disposable restore выполняются в нулевой группе; model/migration checks также
выполняются там. Ручной workflow_dispatch MySQL запускает весь этот набор.
Новые случаи внутри существующих модулей попадают в discovery автоматически.

Параллельность сокращает ожидание, но не обещает меньшего суммарного расхода
runner minutes: создание отдельных тестовых БД и установка зависимостей повторяются.
Скорость зависит от очереди GitHub и длительности самой медленной группы.

## Обязательный результат и выпуск

Имя обязательной проверки `Django checks and tests` сохранено. Этот job запускается
через always(), проверяет результат планирования, policy/configuration и каждого
ожидаемого задания. Ошибка, отмена, неполная matrix, пропуск обязательной группы
или выполнение неожиданного набора не дают зелёного результата. Fail-fast у
матриц выключен, чтобы одна ошибка не уничтожала диагностику остальных групп.
MySQL теперь входит в этот обязательный результат и блокирует deployment при сбое.

Доказательство PR_TESTED_TREE_V1 появляется только после успешного итогового gate.
`reuse_pr_tests.py` проверяет всё дерево, актуальную попытку PR и неизменность всех
семи файлов policy: оба workflow, verifier, selector, runner, MySQL labels и
deployment scope. Изменение любого из них требует полного main CI при первом
выпуске. Неполные/неоднозначные metadata дают обычный полный путь без обхода прав.

Deployment по-прежнему требует успешный итоговый gate, правильное событие/main,
точный SHA, preflight, приватный backup и health HTTP 2xx. Явные status conditions
не позволяют пропущенным необязательным группам блокировать успешный docs-only
выпуск и одновременно запрещают выпуск после отмены или проваленного gate.

Семантика зависимостей, skipped jobs и matrix соответствует
[официальной документации GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).
Сам workflow не отключается path filter: обязательная итоговая проверка всегда
появляется, включая docs-only PR.
