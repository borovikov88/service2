# Обязательные правила работы с калькулятором бассейна

Согласовано с владельцем 23.10.2026. Применяется к `/estimates/` в Service2.
Цель — выполнять запрошенные правки быстро, сохраняя правильность расчётов,
ручные изменения и историю. Новые указания владельца имеют приоритет.

## 1. Область задачи

- Продолжать существующую реализацию. Перед правкой один раз проверить актуальный
  `main`, состояние рабочей ветки и относящийся к задаче код.
- Менять только то, что запросил пользователь. Не добавлять соседние улучшения,
  рефакторинг, общий аудит и новые функции «заодно».
- Не перечитывать всю документацию и не повторять уже подтверждённые запросы.
- Не спрашивать повторное разрешение на ранее согласованные действия.

## 2. Проверки по размеру и риску изменения

Перед запуском проверки определить, какую конкретную ошибку она должна выявить.
Если связь с изменением отсутствует, проверку не запускать.

| Изменение | Достаточная локальная проверка |
| --- | --- |
| Только правила, документация, комментарии | Diff, ссылки и отсутствие случайных изменений. Без Django и браузера. |
| Название, подпись, отдельная кнопка | Проверить изменённый элемент. Не запускать всю регрессию калькулятора. |
| Цена, единица продажи, локальный пересчёт | Проверить исходную и расчётную единицы, итоговую сумму и сохранение ручной цены. При затронутом сохранении — один целевой сценарий сохранения/загрузки. |
| Количество или связь нескольких строк | Проверить изменённую зависимость, повторный пересчёт без дублей и защиту ручных значений. |
| Вёрстка, переносы, перетаскивание | Проверить затронутый сценарий в браузере; мобильную и настольную ширину — когда изменение влияет на адаптивность. |
| Общие формулы, права, миграции, общие слои | Расширить проверки по конкретным рискам, сохраняя обязательные проверки безопасности. |

- Использовать существующий точечный тест, если он доказывает нужное поведение.
  Новый тест нужен для воспроизводимого дефекта или нового значимого поведения,
  а не для увеличения числа тестов.
- Для простой правки цены не запускать десятки соседних тестов автоматически.
  Если цена меняет общую семантику единиц или сохранения, проверять именно эти пути.
- Не проверять разные ширины экрана при изменении серверной цены или формулы,
  если интерфейс не менялся и нет признака ошибки отображения.
- Полный набор штатно выполняет CI. Не дублировать его локально без конкретного
  основания: межмодульный дефект, недоступный CI или прямое указание владельца.
- Повторять пройденную проверку только после относящегося к ней изменения,
  нового сбоя или замечания ревью. Запуск из привычки запрещён.
- Django check и проверка миграций нужны по затронутому риску; документация,
  подписи и отдельная цена сами по себе не повод проверять миграции.

## 3. Ревью и расход лимитов

- Простая правка подписи, цены или подтверждённого коэффициента не требует
  отдельного агента, если достаточно целевой проверки и штатного CI.
- Независимое ревью требуется для существенных финансовых формул, общих
  механизмов начислений, прав, миграций и других рискованных изменений.
- Обычно достаточно одного исполнителя. Не создавать параллельных исполнителей
  и дублирующих проверяющих без конкретной необходимости.
- Не делать много status-запросов подряд. Для CI/deploy — короткое ограниченное
  ожидание по `AGENTS.md`, затем точный статус без обещания фонового наблюдения.

## 4. Неприкосновенность расчётов

- Сохранять ручные цены, количества, выбор товаров, исключения, порядок строк
  и исторические версии. Не менять сохранённые версии при простом открытии.
- Не угадывать цены, фасовки, единицы и технические характеристики.
  Пересчёт цены рулона/упаковки допустим только по подтверждённой площади/массе.
- Не менять цены и карточки магазина ради исправления калькулятора.
- Не маскировать неизвестное значение нулём. Не выдавать предварительный
  подбор за подтверждённый инженерный расчёт.

## 5. Завершение и публикация

- Согласованные пользовательские правки публиковать штатным путём
  PR → обязательный CI → merge → deploy → health-check, без нового запроса
  разрешения на каждом шаге. Защиты GitHub и production не обходить.
- Документация не требует ручного перезапуска приложения или отдельного
  deployment. Если штатный workflow запускается автоматически, не дублировать его.
- При отказе или блокере сообщать точный шаг и причину. Не повторять запрещённое
  действие без новых существенных оснований.
- В итоге кратко сообщать: что изменено, что проверено и опубликовано ли это
  фактически. Не заменять результат списком коммитов и количеством тестов.
- После доказанного результата остановиться. Не начинать новую проверку
  или соседнюю задачу без причины.
