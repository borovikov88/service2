## Проверяемый результат будущего первого среза

1. Экран «Контакты» с вкладками «Компании», «Поставщики», «Физ лица»;
   прежние URL карточек и Client IDs остаются действующими.
2. Одна компания может быть и клиентом, и поставщиком; обе вкладки ведут

   поставщиков, без копирования человека или его телефона.
3. Ни вкладка, ни роль поставщика не предоставляют доступ к источникам,
   финансовым данным или личным контактам и не меняют создание лидов.
4. Нет автоматической классификации, объединения, изменения 1С и финансов;
   неизвестный статус остаётся неизвестным.

## Найденные ограничения (код, не доказательство утечки в production)

У Client нет поля личной видимости/владельца приватного контакта. Поэтому
показывать личные телефонные книги через новый экран нельзя. Существующие
org-карточки сохраняют прежнюю доступность; новая классификация «личный» до
отдельного privacy-среза недоступна, иначе название создаст ложную гарантию.

В `clients_list` связи выбираются через OR по доступной company/person. При
некорректной межорганизационной связи другая сторона может попасть в вывод
и search_text. Модель не имеет DB-проверки same-org/type, хотя add endpoint
их проверяет. Перед новым экраном нужен общий фильтр обеих сторон и одинаковой
organization, active_clients для обеих; карточка/lookup/update/delete также
должны перепроверять обе стороны. Не исправлять старые строки молча.

Также вход в список проверяет наличие staff-роли хотя бы в одной organization,
затем выбирает все membership org_ids. При реализации ограничить queryset
организациями с действующим разрешённым доступом (согласованным с карточкой),
включая active user; проверить пользователя с разными ролями в разных org.
Это ограничение выдачи, не выдача новых grants.

## Минимальная реализация

**A. Сначала сохранность и серверная выдача.** Единый queryset допустимых
контактов и связей для списка/поиска/карточки; синтетические cross-org, inactive,
merged и malformed-link тесты. Существующий superuser режим не расширять.
Никакой миграции для этого шага не требуется.

**B. Роли контрагента и три вкладки.** Предлагается небольшая additive-модель
`ClientBusinessRole(client, role, created_by, created_at)` с unique(client, role),
ролями customer/supplier/landlord/other. Это метаданные существующего Client,
не новый справочник людей/компаний. В первом UI редактировать только supplier
существующим правом управления карточкой, с аудитом add/remove; прочие роли
не назначать массово. Источник истины organization — Client, без второго
несогласованного поля. Защитить удаление/merge роли и сохранить аудит.

Компании = все доступные действующие legal, включая поставщиков; Поставщики =
доступные Client с явной supplier ролью (включая физлицо-поставщика);
Физ лица = доступные private. Пересечение вкладок намеренно: один ID, не дубль.
ИП сохраняет существующие legal_form и автоматическую пару company/person;
не размножать supplier роль на связанную карточку автоматически.
Legacy без роли остаётся видимым по типу; пустая вкладка поставщиков говорит
«Поставщики ещё не отмечены», не «В организации нет поставщиков».

Оставить `/clients/` и все reverse names; менять только пользовательские
названия страницы/навигации. Сохранить clients_tab=companies/people, добавить
suppliers, неизвестный tab безопасно возвращает companies. Live search,
debounce, отмена старого запроса и URL state; при серверной пагинации фильтрация
и счётчики до pagination, без загрузки всех контактов в браузер.

**C. Личные контакты и intake — отдельный последующий срез.** Не добавлять
личные записи в общую Client выдачу до единой политики owner-only/явного sharing
для списка, lookup, карточки, связей, merge, экспорта, звонков/диалогов и CRM.
Бизнес-роль не является настройкой видимости. Неклиентское назначение обращения
хранить отдельно от роли контакта: supplier+customer сохраняет продажи;
ручное создание лида по конкретному обращению с прежними source permissions;
«Не продажа» с причиной/автором/историей, без удаления и автообъединения.
В текущем срезе intake/cohort/cutoff не меняются.

## Сохранность и миграционный риск

Шаг B требует новой additive schema migration; сейчас она НЕ написана.
Без RunPython/backfill, пересоздания Client, смены PK/FK или onec_ref.
Pool, ClientOwnedObject, CrmItem, ServiceTask, Conversation, financial bindings,
ClientAccess и import refs остаются на прежних ID. Роли — локальные метаданные,
импорт 1С не должен их стирать; merge переносит объединение ролей, разрешая
unique-конфликты и сохраняя аудит. Не менять классификацию контрагента в 1С.
Проверить все merge/import/delete consumers до включения role editing.

Риск невелик по данным при пустой additive таблице, но существенен по правам:
новый список увеличит заметность уже существующих связей. Поэтому security
регрессии и независимое ревью обязательны. До миграции штатные backup/CI gates.
При откате приложения сохранять новые таблицы/аудит, не reverse после записей.
Живые counts, невалидные связи и классификации не проверялись.
