# Создание в 1С через MCP

Ресурс `/mcp/1c-drafts` использует адрес, параметры HTTPS и область организаций уже подключённой 1С Fresh. Документ и карточка записываются стандартным POST в коллекцию OData. Ответ после записи проверяется новым GET под той же учётной записью. Сотрудник получает код карточки или номер документа и Ref_Key. Сотрудники проводят документы в 1С самостоятельно.

## Подтверждение сотрудника для каждого чата

Новый режим включается только при обоих флагах `ONEC_MCP_DIRECT_DRAFTS_ENABLED=true` и `ONEC_MCP_CHAT_IDENTITY_ENABLED=true`. Требуется миграция `0210_onec_chat_identity`; она добавляет только схему и не включает доступ существующим сотрудникам. Read-only MCP финансов и диагностики сохраняют отдельные audience/scope.

Сотрудник вызывает приложение в ChatGPT. Инструмент `get_chat_identity` показывает кнопку «Подтвердить личность». Она открывает страницу Ровика с именем текущего сотрудника и кнопкой подтверждения. Если входа ещё нет, сначала выполняется обычный вход. Страница не содержит поставщика, товары или документы и не запускает подготовленную запись. После подтверждения приложение возвращает пользователя по выданному ChatGPT адресу; состав документов и новых карточек согласовывается в чате.

Привязка использует `params._meta["openai/session"]` и `params._meta["openai/subject"]` вместе с OAuth grant и организацией. Эти значения не принимаются в аргументах модели. В БД хранится HMAC, а не исходные идентификаторы. Если клиент не передал метаданные беседы, запись закрыта. Метаданные служат границей чата, а личность подтверждает только CSRF-защищённый POST вошедшего сотрудника. Подпись формы привязана к ссылке, одноразовому внутреннему nonce и текущей учётной записи браузера; ручного кода для сотрудника нет.

Подтверждённый чат нельзя переключить на другого сотрудника. Подтверждение нового чата не изменяет `FinanceMcpGrant.authorized_by` и автора уже открытого чата. При каждом вызове, перед записью и перед возвратом результата проверяются действующий OAuth, доступ сотрудника, отсутствие увольнения/служебного аккаунта, подтверждённая привязка автора и текущее подключение 1С. Смена привязки или подключения требует нового чата. Отзыв OAuth закрывает все его чаты.

Автор берётся из существующей `OneCAuthorIdentity`: ровно одна подтверждённая запись со статусом `mapped`, связанная с активным сотрудником этой организации. `EmployeeOneCIdentity` содержит идентификатор зарплатного справочника и здесь не используется. Перед созданием документа проверяются EDM-связь `Автор` с `Catalog_Пользователи`, доступность пользователя, `Недействителен=false`, `Служебный=false`. Произвольный автор из текста запроса не принимается. Непроведённый документ получает этот GUID сразу при POST, без расширения 1С.

При первом GET после создания проверяются реквизиты, строки, `Posted=false` и совпадение автора. `initial_author_matches` сохраняет результат первой проверки; `author_mismatch` означает, что документ уже существует, но 1С вернула другого автора. Его нельзя создавать повторно. `author_ref_key` показывает текущее наблюдение при повторной сверке. Документ, существовавший до запроса, сохраняет своего автора: при совпадении реквизитов и автора возвращается `exists`, при отличиях требуется сверка без повторного создания.

`request_nomenclature` возвращает точные карточки, разрешённые ссылки 1С, `request_id` и `confirmation_digest` для показа в чате. После явного согласия сотрудника вызывается `create_1c_nomenclature` с этой парой. Нет перехода на страницу проверки карточек. Другая беседа, другой сотрудник, изменённый состав или истёкший запрос не могут использовать подтверждение. Наличие digest фиксирует согласованный состав; факт текстового согласия обрабатывает ChatGPT. Собственные системные подтверждения ChatGPT сохраняются.

### Подключение и проверка

1. Сохранить существующие адрес Fresh, HTTPS и область организаций. Явно задать закрытые `ONEC_MCP_DRAFT_USERNAME/PASSWORD` разрешённого подключения. Право на запись ограничивает учётная запись интеграции; заполнение реквизита «Автор» не переключает нативный сеанс 1С на сотрудника.
2. Проверить существующие привязки сотрудников к `OneCAuthorIdentity`, не создавать их по приблизительному совпадению имени. При отсутствии или неоднозначности запись закрывается с понятным сообщением.
3. Выполнить protected release, миграцию, затем включить оба флага. Подключить отдельное OAuth-приложение к `https://service2.aqualine22.ru/mcp/1c-drafts`, scope `service2.onec.drafts`, CIMD-клиент ChatGPT. Подключение само по себе не подтверждает новый чат.
4. Проверить в настоящем клиенте ChatGPT наличие метаданных беседы, отображение кнопки, вход/подтверждение и возврат. Проверить две беседы с разными сотрудниками. Вызов кнопки может показываться по-разному на разных версиях клиента; без проверки нельзя объявлять мобильный переход подтверждённым.
5. Проверить непроведённый тестовый документ и его автора через GET. Проверка не требует проведения. При неизвестном результате POST использовать ту же попытку, не новый запрос.

Официальные контракты: [метаданные запросов и внешний переход](https://developers.openai.com/plugins/reference), [MCP Apps и расширения](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md).

## Предыдущий режим с пустым автором

При включении `ONEC_MCP_DIRECT_DRAFTS_ENABLED=true` ресурс `/mcp/1c-drafts` принимает собственное OAuth-разрешение `service2.onec.drafts`. Сотрудник подключает его через существующий издатель OAuth с PKCE. У каждого поручения в Service2 сохраняется инициатор — сотрудник, авторизовавший подключение. Для различения инициаторов нужны личные подключения.

`create_1c_document` передаёт в стандартный OData `Posted=false` и пустую ссылку `Автор_Key`. Расширение, дополнительные реквизиты и обработчики УНФ не используются. После POST выполняется GET: проверяются номер, ссылка, реквизиты, строки, отсутствие проведения и фактический автор. Если при первой проверке автор уже заполнен, возвращается `author_not_empty` с номером и ссылкой созданного документа. Это результат, требующий проверки, а не основание создать ещё один документ.

Назначение автора при последующей записи или проведении в интерфейсе зависит от конкретного релиза и настроек УНФ. Service2 не перехватывает эти события и не может гарантировать правило «первый сохранивший становится автором». До проверки в рабочей базе это правило считается неподтверждённым. На повторном обращении после подтверждённого создания возвращаются текущее состояние и автор; код не объявляет, кто и каким действием изменил документ.

`author_empty` и `author_ref_key` описывают текущее наблюдение. Отдельно сохраняется `initial_author_empty` — результат первой проверки созданного документа. Если он равен `false`, повторный запрос сохраняет статус `author_not_empty`. У найденного ранее существовавшего документа исходный автор неизвестен (`null`); его ссылка фиксируется, поэтому исправление номера счёта в 1С не превращает повтор запроса в новое создание.

Для создания карточек `request_nomenclature` возвращает приватную ссылку проверки и идентификатор запроса. После подтверждения сотрудником `create_1c_nomenclature` использует этот идентификатор. Переписывать коды в чат не требуется; личные учётные записи для записи карточек сохраняются.

1. В закрытом окружении Service2 задать `ONEC_MCP_DRAFT_USERNAME` и `ONEC_MCP_DRAFT_PASSWORD` для разрешённой учётной записи 1С. Адрес, HTTPS и разрешённые организации берутся из действующего подключения. Вызов ограничен реальными правами этой учётной записи в 1С, а не правами инициатора в нативном интерфейсе.
2. Выполнить штатный выпуск с миграцией `0208_onec_ticketless_drafts`. Настройка нового режима по умолчанию выключена. При включении старые ручные коды закрываются; существующие read-only MCP не получают полномочий на запись.
3. Проверить один явно обозначенный непроведённый тестовый документ: пустой автор сразу после POST/GET; открытие без сохранения; первая успешная запись сотрудником; повторная запись другим сотрудником; затем проведение только по отдельному разрешению владельца. Не проводить тестовый заказ ради проверки, если это запускает реальные хозяйственные действия.
4. Зафиксировать фактический результат в текущем релизе УНФ. Если штатное поведение не назначает первого автора или меняет его позже, согласовать изменение требования. Фоновая перезапись автора из Service2 не заменяет нативное правило и не выполняется.

При потере ответа запрос сверяется по сохранённой ссылке. Если провайдер заменил UUID и ответ с новым UUID потерян, без дополнительного нативного реквизита нельзя надёжно установить связь. В таком случае повторный POST блокируется до ручной сверки. Первичная проверка не принимает изменённые строки или проведённый документ даже при заполненном авторе.

## Предыдущий режим с личными кодами

Сотрудник входит в свою учётную запись Ровика, открывает `/onec/drafts/` и получает код на 15 минут для одного документа либо списка из 1–10 карточек. Он передаёт код в чат с поручением. MCP заполняет запрос, после чего сотрудник проверяет точные значения в личном Ровике и разрешает эту запись. Вызов `create_1c_document` или `create_1c_nomenclature` принимает только тот же код и исполняет только одобренные значения. Пароль 1С через чат не передаётся. Участники общего аккаунта ChatGPT могут видеть историю, включая возвращённые в чат коды и номера. Для частных документов нужен личный чат в отдельной учётной записи.

Для заказа поставщику передавайте артикул или точное название товара, количество, единицу и цену, когда она указана. Если требуется выбор по названию, сотрудник видит варианты на личной странице и выбирает фасовку. В предварительном просмотре представлены фактические связанные объекты 1С. Изменение сопоставления после подтверждения останавливает запись. Если артикул поставщика и внутренний артикул указывают на разные товары, сначала требуется уточнить сопоставление в базе.

Для счёта с НДС, скидками, валютой или договорами передавайте соответствующие реквизиты и суммы в `fields` и `tables` по метаданным. Проверяйте суммы и налоговые реквизиты счёта до подтверждения. Система проверяет присланные ссылки в живой базе и сравнивает реквизиты и строки записанного документа с согласованными значениями. Для новой карточки внутренний артикул проверяется в основном справочнике. До подтверждения фиксируются ссылки на единицу измерения и выбранную группу. Если они изменились к моменту создания, запись останавливается. В записанной карточке проверяются артикул, тип, наименование и единица.

В поставке настроены обязательные реквизиты заказа поставщику и перемещения запасов. Для остальных видов настройте проверенные профили заполнения в серверном `ONEC_MCP_DOCUMENT_PROFILES_JSON`. Ключом служит опубликованное имя документа. Объект каждого профиля содержит список `fields` с обязательными реквизитами и словарь `tables` с именами табличных частей и обязательными колонками. Эти профили описывают обязательное содержимое документа для всех сотрудников. Доступ на добавление и ограничения на уровне записей определяет 1С при вызове. Права основной операции OData и интерактивного добавления в формах могут различаться. Если конфигурация использует такое различие, отдельно проверьте его перед подключением роли. Описание прав доступно у [1С](https://v8.1c.ru/platforma/sistema-prav-dostupa/).

Сотрудник отдельно подтверждает каждое поручение на создание карточек. При неполных исходных данных документа MCP сообщает, что требуется уточнить.

## Настройка подключения

1. Оставьте существующие `ONEC_ODATA_BASE_URL`, `ONEC_ODATA_ORGANIZATION_GUIDS`, `ONEC_ODATA_TARGET_ORGANIZATION_ID`. Введённый через MCP адрес подключения не поддерживается.
2. В закрытом окружении сервиса задайте `ONEC_MCP_WRITE_BINDINGS_JSON` как словарь из идентификатора пользователя Ровика в его личный логин Fresh. Для каждой такой записи задайте пароль в секрете окружения `ONEC_MCP_WRITE_PASSWORD_<id пользователя>`. Администратор сверяет принадлежность каждой учётной записи и действующее право удалённого доступа через OData в целевой базе. Дублирующиеся имена входа блокируются.
3. Для владельца можно использовать действующие `ONEC_ODATA_USERNAME` и `ONEC_ODATA_PASSWORD`, только если это его личная учётная запись 1С. Администратор добавляет явное соответствие логина и указывает его идентификатор в `ONEC_MCP_WRITE_CONNECTION_OWNER_ID`. Каждый вызов дополнительно проверяет текущую роль владельца в целевой организации. Служебный логин диагностического подключения следует оставить без такой привязки.
4. Выполните штатный выпуск Service2 с миграциями. Подключите новый URL MCP в ChatGPT. Подключения диагностики и финансов сохраняют свои отдельные полномочия.

## Повторные запросы

Модуль проверяет существование артикула в доступном справочнике. Для входящего документа проверяются организация, контрагент, номер и дата счёта. Для документа без реквизитов счёта точное повторение утверждённого содержимого определяется по нему самому, в том числе из нового чата. Для отдельного заказа с такими же строками укажите собственную дату документа или отличительный реквизит. Если истёк код ранее отправленного запроса, владелец может в течение двух суток получить новый код к той же записи в личном Ровике. По умолчанию разрешены 10 выдач кодов и до 10 попыток создания объектов в час на сотрудника. Уже существующие объекты не расходуют лимит записи. Создание списка останавливается при первой ошибке и возвращает результаты обработанных строк и число оставшихся.

До отправки в 1С сохраняется постоянная запись о попытке. После обрыва отклика следующий вызов ищет объект в рабочей базе. Если установить результат невозможно, модуль удерживает блокировку повторной отправки. Для разбора используйте Ref_Key попытки и журнал регистрации 1С. Не снимайте блокировку без сверки фактического результата. Защита от параллельных вызовов этого MCP действует в Service2. Независимые ручные операции и сторонние интеграции подчиняются действующим ограничениям уникальности в самой 1С.
