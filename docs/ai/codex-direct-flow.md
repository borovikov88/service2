# Прямой рабочий цикл Service2 из Codex / ChatGPT / Work

Этот документ описывает короткий практический путь от сообщения владельца до
проверенного изменения. Исторические эксперименты с API-review, PR №92/94 и
canary-workflow не являются шагами каждой новой задачи.

## 1. Старт

1. Один раз получить текущий `main` HEAD.
2. Прочитать актуальный `AGENTS.md`. В Codex он может быть загружен
   автоматически; в обычном ChatGPT/Work с GitHub connector его нужно явно
   прочитать один раз на новый рабочий контекст.
3. Если есть локальный worktree — проверить `git status`. Если работа идёт
   только через connector, не делать фиктивную проверку локального состояния.
4. Сформулировать 2–5 критериев готовности.
5. Открыть только относящиеся к задаче документы/файлы.

Не перечитывать весь `docs/ai/`, не проверять HEAD после каждого read-only
действия и не восстанавливать текущее состояние по старым сообщениям чата.

## 2. Выбор уровня риска

**Низкий риск:** документация, подписи, CSS, локальная разметка, небольшая
нефинансовая UI-логика.

**Обычный риск:** локальная бизнес-логика без изменения финансовой формулы,
прав, миграции, OAuth/MCP или production-процесса.

**Высокий риск:** валовая прибыль/ДДС/ФОТ, импорт и unified sync 1С,
организационная изоляция, права, OAuth/MCP, миграции, секреты, recovery,
изменение production-данных и действия во время production-инцидента.

Уровень риска определяет глубину диагностики, тестов и необходимость
независимого ревью. Не применять максимальный процесс к простой подписи или CSS.

## 3. Диагностика

Начать с одного конкретного вопроса: «какого факта не хватает для решения?».

- GitHub: читать нужные файлы/diff/PR, по возможности группировать независимые
  read-only запросы.
- Service2: использовать сохранённые подтверждённые данные приложения, когда
  вопрос относится к управленческому состоянию Service2.
- 1C Diagnostic MCP: использовать только когда нужен фактический источник 1С,
  схема OData, связь документа или проверка ошибки импорта. Запрос должен быть
  bounded и read-only: конкретный entity, поля и фильтры вместо каталожного дампа.
- Не повторять тот же запрос без новой причины. Если результат уже доказывает
  гипотезу, переходить к исправлению/выводу.

Для текущей финансовой архитектуры помнить:

- страницы не должны читать live 1С при обычном просмотре;
- direct-order expense — себестоимость заказа, а не платёж ДДС;
- заказ/клиент определяется валидной связью заказа и настроенным scope
  организаций, а не поставщиком приходной накладной;
- Finance MCP и 1C Diagnostic MCP имеют разные resource/scope и не заменяют друг
  друга;
- персональные зарплатные значения и source payload не выводятся в Git/логи.

## 4. Реализация

Работать в отдельной ветке/PR, если меняется репозиторий. Перед первым write,
если диагностика заняла заметное время или `main` мог измениться, повторно
сверить base HEAD.

Не расширять scope попутным рефакторингом. Если найдена соседняя проблема,
зафиксировать её отдельно и не смешивать с текущим PR без необходимости.

## 5. Проверки

Использовать минимально достаточный локальный набор:

- docs-only: diff/структура/ссылки, без Django suite;
- UI/template/CSS: целевой тест при наличии + Django check, если применимо;
- обычная логика: целевые regression tests + Django check;
- finance/import/access/OAuth/MCP/migrations: целевые regression/security tests,
  Django check и migration dry-run.

Полный Django suite штатно выполняет GitHub CI. Не запускать его локально
повторно после каждого мелкого изменения. Повтор широкого набора оправдан после
изменения кода по замечанию, при реальном признаке регрессии или когда CI не
может дать нужного доказательства.

## 6. Независимое ревью

Отдельный проверяющий обязателен для high-risk изменений: финансовые формулы,
импорт 1С, права/организационная изоляция, OAuth/MCP, миграции, безопасность и
опасный production/recovery diff.

Для docs/UI/малого локального исправления независимый субагент не создаётся
автоматически: это лишние время и кредиты, если риск закрыт целевым тестом и CI.

Проверяющий получает финальный diff/head и критерии задачи. Если после review
код изменился существенно, high-risk diff проверяется повторно.

Формальный GitHub `APPROVED` не считается универсальным gate, если текущие
ruleset/workflow этого не требуют. Обязательны реальные действующие guards и
зелёный CI. Не использовать старые сохранённые approval или legacy publisher.

## 7. CI, merge и deployment

Текущий обязательный CI определяется
`.github/workflows/ci-deploy.yml`: Django checks, migration check и полный
test suite. После попадания точного commit в `main` deployment может идти
только после успешного test job и действующих production guards.

Перед merge/deployment:

1. проверить, что PR соответствует исходной задаче;
2. проверить актуальный head и зелёный CI;
3. убедиться, что нет нерешённых замечаний high-risk review;
4. не обходить branch/environment/preflight правила;
5. production deployment выполнять exact tested commit;
6. после deployment требовать health-check/smoke.

Миграции, импорт, изменение production-данных, секретов, классификаций или прав
доступа требуют явной области задачи и не выполняются «в нагрузку» к UI/bugfix.

## 8. Production-инцидент

При HTTP 500, массовой ошибке или деградации:

1. остановить необязательные оптимизации и новые feature-изменения;
2. установить production HEAD;
3. получить свежую конкретную ошибку/traceback;
4. сравнить production с текущим `main` и определить минимальный виновный diff;
5. сделать минимальный fix либо безопасный rollback;
6. выполнить целевые проверки и production health/smoke;
7. только после восстановления продолжить плановую работу.

Не запускать широкие рефакторинги во время восстановления.

## 9. Ограничение длинных tool-цепочек

Чтобы чат не оставался надолго без ответа:

- после примерно 5–8 существенных внешних вызовов дать короткую контрольную
  точку владельцу, если итог ещё не готов;
- сообщать только три вещи: что подтверждено, что выполняется дальше, есть ли
  блокер;
- контрольная точка не останавливает задачу и не требует ответа владельца:
  после сообщения продолжать автоматически с того же фактического состояния,
  если нет реального блокера, нового разрешения или решения владельца;
- не повторять уже сделанные чтения/тесты;
- исключение — один атомарный короткий batch, который безопаснее закончить
  целиком.

Цель — не искусственно уменьшить полезную проверку, а исключить десятки
повторных запросов и длинные молчащие цепочки.

## 10. Авторизация и retired пути

Разработка и review используют выбранный владельцем путь ChatGPT/Codex.
Не добавлять отдельно оплачиваемый `OPENAI_API_KEY`, API fallback, browser
cookies или `auth.json`.

Для Service2/Finance MCP и 1C Diagnostic MCP в пределах одной задачи сохранять
и повторно использовать уже работающее connection/link. Не запускать новый
OAuth flow после каждого tool-вызова и не выбирать другой дублирующий `link_id`
без причины. Повторная авторизация оправдана только после явного сигнала
платформы/tool об отсутствии, истечении или отзыве авторизации либо о
необходимости нового consent. Permission-подтверждения самого ChatGPT являются
отдельным уровнем безопасности и не обходятся правилами репозитория.

`direct-pr-review.yml` и legacy `development-codex.yml` не являются
штатным модельным review-путём и не должны использоваться для обхода текущих
правил. Canary/connection workflow — диагностические инструменты, а не
обязательный этап каждого PR.

## Итог владельцу

После задачи коротко сообщить:

- что именно изменено;
- чем доказано;
- PR/commit и опубликовано ли изменение;
- что осталось нерешённым или требует отдельной задачи.

Не продолжать исследование после выполнения критериев готовности.
