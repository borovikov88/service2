# Прямой рабочий цикл Service2

Практический порядок для задачи владельца. Постоянные ограничения и архитектурные
контракты находятся в [AGENTS.md](../../AGENTS.md), фактический GitHub/deployment —
в [deployment.md](deployment.md). Не воспроизводите старые API-review/canary шаги.

## 1. Определить результат и источник истины

- Получить текущий main и прочитать AGENTS один раз на новый рабочий контекст.
  При наличии checkout проверить git status; при работе только через connector
  не изображать локальную проверку.
- Сформулировать 2–5 критериев результата и определить риск изменения.
- Открыть затронутые файлы, их зависимости и относящиеся к задаче тесты.
  [project-context.md](project-context.md) — карта модулей,
  [project-status.md](project-status.md) — датированный журнал, а не доказательство
  текущего production. Проверять реализацию другого чата по фактическому main/diff.
- Использовать уже данную авторизацию в её пределах. Не повторять вопрос о
  согласованном следующем шаге; новую область данных/прав/публикации не выводить
  из одного наличия технического доступа.

## 2. Проверить одну гипотезу и изменить существующую реализацию

Пакетировать независимые чтения. Для каждого запроса понимать недостающий факт;
после его получения переходить к решению. Не читать весь архив и не перепроверять
тот же HEAD после каждого чтения. Повторно сверить базу перед записью, если она
могла измениться, и перед merge.

Для обычного UI/кода не требуется live 1С. Для вопроса об источнике использовать
ограниченный read-only Diagnostic-запрос. Рабочие суммы, секреты, полные payload
и персональные сведения не переносить в Git или журналы.

Работать в отдельной ветке/PR. Сохранять текущие CRM command/intake services,
эпизоды обращений, права на звонки/задачи и организационную изоляцию. Не создавать
параллельный механизм и не добавлять соседний рефакторинг для заполнения ожидания.
Правка кода не означает разрешение на массовую обработку production-истории.

## 3. Подготовить проверенного кандидата

Выбирать локальные проверки по риску из AGENTS: документации достаточно diff,
структуры и ссылок; логике — целевых regression tests; общим данным, правам и
миграциям — соответствующих security/DB checks. Все обращения к локальной
тестовой БД выполняются с --settings=service_site.test_settings.

До тяжёлого GitHub-запуска по возможности завершить локальную проверку и нужное
независимое ревью. После изменения общего JS/шаблона проверять затронутые
браузерные сценарии и загрузку актуальных файлов. Не запускать локально весь
suite вслед за каждым исправлением, которое уже покрыто целевым тестом и CI.

Для финансов, прав/изоляции, OAuth/MCP, миграций, безопасности и опасных
production-изменений независимый проверяющий получает фактический final diff/head
и критерии. Для обычных docs/UI не создавать отдельного агента по формальности.
Содержательное замечание закрыть малым fix-cycle; получить заключение на конечном
head. Формальное GitHub APPROVED требуется по действующим настройкам, а не по
историческому примеру другого PR.

## 4. Провести CI, merge и разрешённый выпуск

Текущий CI описан в ci.md, deployment.md и YAML. Он консервативно выбирает
docs/calculator/известный UI по полному diff; бизнес-логика и неизвестные пути
включают полный набор. Серверные, браузерные и MySQL-группы идут параллельно;
обязательный итоговый gate проверяет все выбранные задания.
Рекомендация о коротком локальном наборе не является разрешением обойти этот gate.
При совпадении дерева main с проверенным PR результат может использоваться
повторно через существующий проверяющий script.

Проверить final head, фактический зелёный CI, отсутствие неразрешённых замечаний
и текущую базу. Выполнить разрешённый обычный merge без bypass. Для production
требуются точный tested commit, preflight, проверенная приватная копия БД,
штатные блокировки и успешный health-check. Занятый lock не удалять, рабочий
процесс не останавливать; проверять текущий attempt перед повтором нужного этапа.

Ожидать обязательный gate доступным штатным способом и читать компактный статус,
не полные логи каждые несколько секунд. Ожидание не требует нового «продолжай».
При конкретном сбое изучить нужный traceback и исправить причину в пределах
задачи. Если нужно решение владельца или продолжение технически невозможно,
дать точный статус/head/run и оставшийся шаг, не объявляя выпуск успешным.

## 5. Подтвердить результат и остановиться

Выполнить один короткий smoke по критериям задачи. Проверку UI, не требующую
изменения бизнес-данных, проводить без сохранения случайных рабочих карточек.
Снимок должен показывать результат и не раскрывать лишние сведения; повторять
проверки или оформление при найденной ошибке, а не ради размера отчёта.

Сообщить, что изменилось, чем проверено, что фактически опубликовано и какие
существенные ограничения остались. Разделять время реализации, CI и выкладки.
Синтетические времена не представлять как измерения на production.

При инциденте сначала восстановить работу минимальным fix/безопасным rollback
и health-check; затем возвращаться к плановым изменениям. После достижения
критериев не начинать соседний аудит.

## Подключения и retired пути

Повторно использовать исправное Service2/Finance MCP или 1C Diagnostic соединение
и тот же link_id. Новый вход нужен после явного сообщения об отсутствии,
истечении/отзыве авторизации или новом consent. Не обходить permission prompts.

Разработка и review используют выбранную владельцем авторизацию ChatGPT/Codex.
Отдельный платный API fallback, OPENAI_API_KEY, browser cookies и auth.json
не добавляются. Наличие legacy workflow не делает его текущим модельным
review/publisher-путём.
