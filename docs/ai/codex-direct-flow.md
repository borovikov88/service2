# Прямой цикл задачи из Codex-чата

## Текущее состояние

Владелец ставит задачу ведущему в Codex. Разработка, отдельная проверка и
исправления внутри активной сессии проходят по `AGENTS.md`. Сообщение чата
не создаёт `DevelopmentTask` в production и не запускает серверный poller.

5 сентября 2026 года GitHub connector позволил читать remote refs, создавать
и обновлять ветки/PR. PR №88 и №89 объединены владельцем; исходный `main`
для этой задачи — `fa1f7de419457703c6f5fd8c590de8485e4e27ed`. Ограничения shell
не означают отсутствия доступа через connector. Старые указания обновлять
только PR №87 относились к предыдущему checkout и больше не описывают текущую
задачу. Для новых изменений создаётся новый PR от проверенного `main`; для
исправлений уже открытого PR обновляется его ветка, без дубликатов.

## Независимая проверка прямого PR

Статус реализации: **черновик, не готов к merge**. 22 локальных теста прошли,
но финальное независимое ревью прервано ошибкой лимита кредитов workspace.
Первое замечание о потере executable mode в контексте исправлено и покрыто
тестом; повторное принятие проверяющим ещё не получено. Внешние вызовы модели
и публикация review этим новым workflow не проверены.

`direct-pr-review.yml` и `.github/scripts/review_direct_pr.py` добавляют отдельный
путь для PR, созданных непосредственно из Codex. Исходную задачу и критерии
готовности ведущий помещает в описание PR: GitHub workflow не видит историю
личного чата. Недостаточный контекст не должен превращаться в одобрение.

Проверяющий получает описание задачи, инструкции базовой версии проекта,
изменённые исходники до/после и diff. Файлы PR передаются как данные модели;
код PR, его зависимости и workflow не выполняются в job с секретами.
Модель не получает токен reviewer identity и не имеет инструментов записи.
Это анализ исходников; Django-тесты запускает отдельный CI.

Отдельный publisher получает результат из artifact того же workflow run и
проверяет repo, номер PR, автора, base/head SHA и неизменность описания задачи.
Только после этого публикует решение от `aqualine-review-bot` с точным
`commit_id`. Ошибка модели, неполный ответ, недостаточный контекст или смена
коммита не дают `APPROVED`. Локальный `ACCEPT` не заменяет этот GitHub review.

Автоматические события относятся только к разрешённым PR внутри
`borovikov88/service2` в `main`. Ручной запуск — только владельцем с доверенного
`main`. Изменения PR запускают новую проверку; чужой fork не получает секретов.
При добавлении workflow в `main` отдельный read-only job проверяет identity
бота и наличие ключа OpenAI без публикации review, merge или deployment.

## Однократная настройка

- Аккаунт `aqualine-review-bot` приглашён в публичный `borovikov88/service2`;
  право `write` подтверждено GitHub API.
- Владелец сообщил о сохранении classic PAT `public_repo` как Environment
  `review` → secret `SERVICE2_REVIEW_TOKEN`. Значение не передаётся в чат/Git.
- Reviewer job использует repository secret `OPENAI_API_KEY`, как существующий
  `development-codex.yml`. Наличие имени в workflow не доказывает, что ключ
  сохранён, действителен или имеет доступ к модели.
- В настройках Environment `review` следует разрешить только ветку `main`.
  Доверенный workflow дополнительно проверяет события и refs. Само Environment
  не создаёт ограничений, пока они не настроены владельцем.

Первый PR, добавляющий этот workflow, не может проверять себя ещё не установленным
workflow базовой ветки. Он проходит отдельное ревью и обычный CI; после попадания
в `main` проверяется подключение и затем отдельный реальный PR. До внешнего
успешного результата нельзя утверждать, что бот уже работает.

## Что пока не автоматизировано

Новый путь публикует review, но не включает auto-merge и не меняет deploy gate.
На момент проверки `allow_auto_merge=false`. Чтение branch protection через
connector вернуло 403; его наличие и настройки этим запросом не установлены.
Перед включением автоматического merge нужны действующие required checks,
актуальный независимый approval и dismissal stale approvals.

Ведущий может прочитать замечания и исправить их в активной Codex-сессии.
Автоматический запуск разработчика по замечанию, когда сессия закончилась,
остаётся незавершённым звеном. Этот workflow не обещает фоновый цикл исправлений.
Существующий `DevelopmentTask` review/correction/delivery остаётся отдельным.

SSH из GitHub Actions проверен run `33967180783` (`SSH_KEY_OK`,
`HOSTING_LAYOUT_OK`, `HEALTH_HTTP=200`), но первый deployment нового pipeline
не выполнен. Финансовый советник и MCP ещё не подключены к реальным данным.
