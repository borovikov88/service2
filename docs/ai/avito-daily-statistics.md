# Services daily-statistics foundation

Scope is connection 4/account 446312402. This continues the existing stats-v2 reader and existing native monitor. It performs official read calls only. No promotion purchase, source setting, listing content, customer message, finance calculation or 1C data is changed.

Two additive tables retain collection provenance and daily item facts. Each invocation reads at most one API page, with the existing account/method throttle and a scoped DB lease. Partial pages are resumed without sleeping. The complete page count must be confirmed by dataTotalCount; missing total, changing totals, duplicate item IDs or bounds do not become a complete day. Only a completed binding-verified run replaces current daily facts. Missing provider rows/metrics are unknown, including when the provider returns an empty report.

The available date-only contract does not establish the provider's day timezone or an hourly/offset option. provider_timezone=unknown and requested_calendar=Asia/Barnaul are deliberately separate. The collector uses a visible two-day lag, not yesterday disguised as another date. True yesterday/previous-day,7/prior7,30 full Barnaul-day comparisons remain blocked. Separate aggregates are explicitly sums of provider-date counters, not unique people or exact local days. Changing date labels cannot repair this boundary.

Source counters retain contacts, phone, messenger and their intersection independently. None is not zero. Percentages are calculated only from available matching counters with positive denominators. Cost per contact uses reported cash spending in RUB, converted once from the existing documented kopeks metrics. allSpending, cash, presence/target actions, promotion, other spending and commission remain separate; they must not be added as disjoint costs. Unconfirmed bonus units and raw provider average/conversion fields are excluded.

Service labels are exact ServiceType, otherwise the published announcement Title. They are labels, not keyword-based attribution. City prefers explicit City; otherwise an unambiguous exact comma-delimited token Барнаул/Бийск/Горно-Алтайск (optionally г./город) is accepted from published Address with city_source=published_address_exact_token. Street/title substrings, ambiguous cities and unsupported geography stay unknown; no geocoder or historical geography claim is introduced. Current published dimensions are stamped at collection; historical geography/category is not invented for a backfill. Missing city stays unknown. Existing append-only feed history supplies the change journal. Observed promo spending does not prove a promotion purchase or its causal effect. Typed manual Item-API VAS observations supplement that journal without extra requests. Presence/null/empty are distinct; a first observed state is a baseline, not purchase or activation history. Typed manual photo proof is excluded from edit dates and protected from unrelated verify events. Promotion purchase history, Wordstat, experiments and recommendations remain later work.

The existing CRM remains authoritative. A bounded read-only coverage projection uses stored provider_context.item.id with a fresh same-account ownership observation, plus explicit and authorized Client FK. Calls without source identifiers and all unsupported lead/order/payment joins remain unknown. Conversations/calls, unique clients, leads, orders, payments and revenue must remain separate. No phone/title similarity join and no new CRM lead/order model are introduced.

The existing protected deploy workplace setup enables collection once when the configuration key is absent, reads at most one page, and preserves explicit owner opt-out on every subsequent deployment. This first read is labelled protected_deploy_first_read, separately from natural monitor evidence. The existing native monitor resumes/backfills one due page per tick; no additional cron or workflow is created. Authenticated channel-admin controls and a protected exact-main command are also available:
python manage.py collect_avito_daily_statistics --connection-id 4 --account-id 446312402 --action enable --expected-sha <reviewed current main>
with SERVICE2_AVITO_DAILY_STATISTICS_SETUP=1. Status/enable/collection are separate facts. Actual API access, provider-day alignment and natural background execution require production evidence; a schema or passing CI alone does not prove them.

## Source-period comparisons and independent coverage

The authenticated read model separates completed API pages, known ad-row coverage, per-metric coverage, and calendar alignment. Its manifest is the published snapshot plus the provider's returned item identities at collection time; it is not a historical active-inventory reconstruction. A page-complete day can still lack known ads or metrics. Deleted/mismatched daily facts do not create zero values or a complete comparison. A fact must match its completed run's connection, account, organization and exact source date.

Source-date windows are anchored visibly at D-2: one date and its predecessor, 7 dates and their previous 7, and 30 dates. Current/prior deltas require complete dates and ad rows, a stable identical known cohort throughout both periods, and known values for the metric. Changes in rates use percentage points; relative changes require a positive prior denominator. A missing metric blocks its own delta. None is never turned into zero. Source, exact inclusive boundaries, run references, fetch time and per-metric coverage stay attached. These comparisons are not full Barnaul-day comparisons and do not count unique people or orders.

The UI shows progress across the 30 requested dates and the next allowed attempt. The collector, existing leases, cursor resume, one-page-per-tick limit and method/account throttle are unchanged. Cash and documented RUB spending categories stay separate. Bonus spending is displayed explicitly as unavailable because spendingBonus units are unconfirmed; subtracting cash from allSpending is not a supported substitute.

## Closed production coverage receipt

The existing protected setup appends source_period_evidence using the same bounded, scope-filtered history and period helpers. It reads database facts only, without full CRM display, new provider calls, or a repeated first collection on later deploys. Its fixed five windows expose only source dates, page/ad coverage counts and booleans; no metric values, money, client data, raw provider fields or source URLs enter the receipt. comparison_available is deliberately strict: every requested metric in the matching pair must be comparable. The 30-date window has no previous30-date peer and comparison_applicable=false. This metadata is evidence about saved coverage, not a blanket confirmation of full Barnaul-day analytics.

## Per-announcement decision report

The same saved, scoped history now supplies five per-announcement windows and the two 1/1 and7/7 comparisons. Expected ad rows are requirements for comparing the selected announcement, not evidence that it was active on every historic date. A missing source date, missing row, unknown manifest membership, duplicate fact or mismatched latest source-run ID cannot become a complete metric. One announcement's incomplete rows do not hide another announcement's complete period. Values use existing normalized RUB metrics once; derived ratios retain positive-denominator checks.

The short management report separates account-wide complete values from per-ad known values. It offers at most three data-grounded actions with actual announcement IDs: reviewing the quality of known contacts, inspecting missing provider rows, or investigating a descriptive cash-cost-per-contact change. Efficiency-change guidance requires two fully comparable periods, at least100 views and10 contacts per period and a50% cost increase; these are conservative diagnostic thresholds, not statistical confidence or causal proof. Sparse data is labelled explicitly. No content, promotion, message, CRM order, notification or provider setting changes as a result of a recommendation.

The background collector, cursor, lease, deadline, native scheduling and account/method throttle are unchanged. This release does not create a second collector or a drain loop. Progress across30 source dates remains independent from completeness of fields. A fixed completion ETA is not promised because a source date may need more than one page, be throttled or require retry.

The existing protected source_period_evidence includes a closed decision_report metadata projection: bounded ad/coverage counts and up to three safe action codes/announcement IDs. It excludes metric values, money, titles, addresses, clients and provider payloads. This proves the saved read model was evaluated; it does not prove all periods are complete or aligned with Barnaul.

The internal DB-only decision_evidence(connection, actor, identifiers, now=None) API lets proposal workflows reuse the same per-ad coverage and current published membership. It reloads the current Services connection, preserves existing organization/channel-management and binding checks, and returns fixed metadata/known-value booleans with source-run IDs and timestamps. Its basis digest tracks coverage/provenance and publication revision, not raw monetary values or request time. Published membership is not active provider status, exact input-file correlation or content verification. No new HTTP/MCP endpoint or provider request is introduced.

## Fair progress across missing source dates

When no valid in-progress run owns the page cursor, the existing collector first selects a missing date that has never been attempted under the current connection/account/organization/source/binding. Ties retain newest-date-first order. After every missing date has an attempt, it selects the date whose latest run has the lowest primary key: a durable attempt sequence that remains deterministic under equal or drifting wall clocks. Each failed retry creates a newer run, so a permanently failing date cannot indefinitely block another missing date. The database aggregates the latest run reference per date; it does not load an unbounded attempt history.

Completed-date validity is unchanged. An existing valid partial run still resumes before selecting another date. The same global next_due_at, 15-minute failure backoff, lease/generation checks, one-page invocation limit and account/method throttle remain authoritative. This is neither a drain loop nor an extra collector, scheduler or provider call. A failed date is never marked complete or converted into zero metrics to advance progress. The moving D-2 cutoff and 30-date window remain unchanged; no provider retention boundary is assumed from local scheduling or a generic error.
