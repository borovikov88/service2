# Одноразовое согласованное включение CRM

## Задача и границы

26 октября 2026 владелец явно поручил включить CRM и открыть её сотрудникам
с ролью менеджера в рамках их прав. Операция
`crm-aqualine-managers-20261026` относится только к организации `1` и
подтверждённому аккаунту инициатора `5`. Его ожидаемая роль в приложении —
`admin`; бизнес-статус владельца не подменяет серверную роль `owner`.

Операция включает `crm_v2_read` и `crm_v2_write`, создаёт только отсутствующие
канонические воронки и стадии и выдаёт инициатору и текущим действующим
менеджерам пять существующих CRM-прав:

- `view_team_deals` — просмотр сделок команды;
- `create_own_deals` — создание своих сделок;
- `edit_own_deals` — изменение своих сделок;
- `transition_own_deals` — смена стадий своих сделок;
- `manage_own_next_action` — управление своим следующим действием.

Список менеджеров определяется по текущим членствам этой организации.
Неактивные аккаунты и сотрудники с неактивной или закрытой кадровой записью
исключаются. Отсутствующая кадровая запись сама по себе не отменяет действующее
членство: это соответствует существующей политике CRM.

Все остальные роли, существующие CRM-права и финансовые настройки сохраняются.
Проверки владения сделкой, приватности задач, организации, подписки и текущих
прав продолжают выполнять существующие сервисы. Публичное включение пилота
через браузер по-прежнему доступно только роли `owner`. Новых web-endpoint,
миграций и переноса старых данных нет.

## Приёмка

1. Свежая проверка аккаунта инициатора, организации, роли и кадрового статуса
   выполняется до изменения прав.
2. Выдача, настройки, bootstrap и журнал фиксируются одной транзакцией;
   ошибка отменяет всю операцию.
3. Повтор с тем же разрешением не выдаёт права повторно, не восстанавливает
   отозванные права и не добавляет новых менеджеров. Результат отражает текущее
   состояние доступа.
4. Менеджер может создавать и изменять свои сделки, но не изменять чужие
   сделки и не читать чужие приватные задачи.
5. Production подтверждается результатом защищённого запуска и открытием
   `/crm/workspace/?org_id=1` в действующем пользовательском сеансе.

## Запуск и журнал

Команда `provision_approved_crm_access` имеет фиксированную область действия.
Без `--apply` она только проверяет состояние. Применение требует точного
`--approval-id crm-aqualine-managers-20261026`, `--expected-sha`, положительных
`--run-id` и `--run-attempt` и контекста `SERVICE2_CRM_APPROVED_ACCESS=1`.
Она не принимает произвольные организации, пользователей или наборы прав.

Рабочий запуск выполняется только штатным workflow `ci-deploy.yml` после
полного CI, preflight, deployment и HTTPS health-check. Дополнительный шаг
срабатывает только для push в `main` с маркером
`[crm-aqualine-managers-20261026]` в сообщении merge-коммита.
Обычный deployment и ручной recovery без этого push-маркера выдачу не запускают.

Remote helper удерживает штатную исключительную блокировку deployment,
проверяет точный HEAD, текущий remote `main`, чистоту кода, origin и маркер,
затем вызывает только эту фиксированную команду. Учётные данные не копируются
в чат, новые полномочия workflow не добавляются.

В рабочей базе `DataAuditLog` сохраняет одноразовый результат вместе с
изменениями. Исполнитель — защищённый deployment, а не вымышленный вход
пользователя через owner-форму: `actor=NULL`, отдельно указаны инициатор,
разрешение, SHA и конкретный GitHub Actions run/attempt. Повтор использует
этот журнал как маркер завершения, сохраняя последующие решения об отзыве.

SSH stdout/stderr остаются во временных закрытых файлах runner и удаляются
после шага. В публичный лог попадает только проверенный агрегированный receipt:
SHA и запуск, флаги CRM, результат проверки доступа и количества менеджеров,
созданных настроек и изменённых назначений. Имена, контакты, кадровые сведения
и списки пользовательских ID в лог не выводятся.

## Проверки и дальнейшие изменения

Целевые Django-тесты проверяют границы выдачи, откат, повтор и существующие
проверки владения и приватности. Они включены также в MySQL CI. Offline-тесты
проверяют настоящий shell/Git/flock-контур на синтетическом checkout и строгую
фильтрацию receipt. Полный Django CI остаётся штатным gate.

Изменение deploy workflow требует полного прогона после merge: механизм
повторного использования PR-тестов специально не изменён. Зелёный CI на
фикстурах не является доказательством выдачи production-прав; необходимы
receipt реального запуска и проверка пользовательского входа.

Это одноразовое назначение. Новый набор сотрудников, изменение ролей или
повторная выдача отозванных прав требуют отдельной явной задачи и отдельной
проверяемой операции; существующий маркер для этого не удаляется.
