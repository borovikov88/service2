# Контракт документов валовой прибыли 1С

Дата проверки схемы: **9 сентября 2026 года**. Контракт относится к GET-only
чтению `AccumulationRegister_Продажи_RecordType` и не разрешает запись в 1С,
автоматическую публикацию или deployment.

## Поля регистра

Для каждой активной строки импорт получает прежние финансовые и аналитические
поля, а также типизированную идентичность документа:

| Поле | Назначение |
|---|---|
| `Recorder`, `Recorder_Type`, `LineNumber` | стабильная идентичность движения; проверка дублей остаётся `Recorder + LineNumber` |
| `Документ`, `Документ_Type` | дополнительная типизированная ссылка; сама по себе не является ключом группировки |
| `Period` | календарная дата движения 1С до перевода timestamp в UTC |
| `Организация_Key` | обязательная проверка allowlist и граница retail-сопоставления |

Типы принимаются только в форме `StandardODATA.Document_*`. Неизвестный, но
безопасный тип не используется для дополнительного запроса: строка получает
отдельный recorder-key и нейтральную подпись. Значение другого семейства,
например `Catalog_*`, отклоняется.

## Разрешённое enrichment

Импорт запрашивает только фиксированные entity sets и поля:

| Entity set | GET-поля | Русская подпись |
|---|---|---|
| `Document_РасходнаяНакладная` | `Ref_Key`, `Number`, `Date`, `Заказ`, `Заказ_Type` | «Расходная накладная» |
| `Document_ОтчетОРозничныхПродажах` | `Ref_Key`, `Number`, `Date` | «Отчёт о розничных продажах» |
| `Document_ЧекККМ` | `Ref_Key`, `Number`, `Date` | «Чек ККМ» |
| `Document_ЗаказПокупателя` | `Ref_Key`, `Number`, `Date` | «Заказ покупателя» |

Все запросы наследуют прежние запрет redirects, same-origin/base-path guard,
лимиты страниц/строк и проверку точного набора запрошенных GUID. Номер и дата
не берутся из регистра на доверии. Не найденная первичная карточка известного
регистратора останавливает draft. Не найденный `Заказ` допустим и не сохраняется
как разрешённая связь.

## Ключ и подпись карточки

Snapshot `onec_odata_profit_draft_v2` (`odata-2`) сохраняет в `source_data`:

- `recorder_type`, исходные document type/GUID и проверенные номер/дату;
- `document_group_recorder`, `document_group_recorder_type`;
- `document_group_key`, включающий локальный ID организации, тип и GUID регистратора;
- `document_display` вида «Расходная накладная №РН-000001 от 09.09.2026»;
- только для найденного заказа — отдельные `resolved_order_*` поля.

При подтверждении ключ заново вычисляется из organization-bound полей, а типы,
GUID, длины, ISO-даты и display проверяются. Для self-group номер и дата группы
обязаны совпадать с номером и датой первичного документа. Для retail-связи
номер, дата и display обязаны совпадать с единственным фактическим target-report
в том же snapshot. Календарная дата сохранённого `period` обязана совпадать с
`source_date`. Поля находятся в JSON, поэтому миграция БД не требуется.
Изменение ключа не меняет число исходных строк и не пересчитывает выручку,
себестоимость или валовую прибыль.

## Правила объединения

1. Обычные строки объединяются только по recorder identity одной организации.
   Ссылка `Заказ` — аудитная дополнительная связь, не группировочный ключ.
2. Строка `Document_ЧекККМ` может использовать ключ
   `Document_ОтчетОРозничныхПродажах` только когда в той же организации и в ту
   же календарную дату 1С найден ровно один разрешённый отчёт. При нуле или
   нескольких отчётах чек остаётся отдельным.
3. Сумма, покупатель и близость дат не используются вне этого typed retail
   guard. Retail snapshot дополнительно требует
   `source_date == check Date == report Date`.
4. Dashboard группирует по `document_group_key`; XLSX и старые строки без ключа
   используют прежний `document_name`.
5. Только строки нового проверенного OData-контракта с явным group key и полной
   recorder/group identity могут показываться одной строкой для точной пары
   revenue-only/cost-only с одинаковыми периодом, номенклатурой, артикулом,
   типом, менеджером и совместимым количеством. XLSX, старый OData и неполная
   metadata никогда не схлопываются эвристически. Это presentation-only: строки
   БД и итоги не меняются; при сомнении движения показываются отдельно.

## Наблюдаемая схема сентября 2026

GET-only диагностика подтвердила `Recorder`, `Recorder_Type`, `Документ`,
`Документ_Type`; у расходной накладной отдельные revenue-only и cost-only
движения имеют один Recorder. Ссылка `Заказ` разрешается лишь у части документов;
одна общая неразрешённая ссылка наблюдалась у нескольких строк и потому не может
быть основанием объединения.

Для розницы на датах 1, 2, 3, 4 и 9 сентября наблюдалось ровно по одному отчёту
о розничных продажах; строки чеков на этих датах имели количества 2, 7, 3, 1 и
5. Явной scalar-ссылки чек → отчёт схема не предоставила, поэтому действует
только узкое правило уникального typed report за organization/date.
