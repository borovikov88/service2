# Подключение Авито к коммуникациям

Интеграция работает отдельно для каждого `ChannelConnection`, поэтому одна
организация может подключить несколько аккаунтов Авито. В `external_id`
подключения указывается числовой ID аккаунта Авито.

## Настройка

Основной путь настройки — интерфейс Service2:

1. Откройте **Коммуникации → Каналы связи → Авито → Добавить подключение**.
2. Укажите название подключения, числовой ID аккаунта Авито, `client_id` и
   `client_secret`. Секреты не отображаются после сохранения и хранятся только
   в зашифрованном виде.
3. После сохранения нажмите **Подключить Авито**. Service2 сам получает
   access token по `client_credentials`, запрашивает фактический ID аккаунта
   через `GET /core/v1/accounts/self`, при необходимости исправляет сохранённый
   ID, проверяет доступ к Messenger API, создаёт новый секретный webhook URL,
   регистрирует его через `POST /messenger/v3/webhook` и подтверждает наличие
   подписки через `POST /messenger/v1/subscriptions`.
4. Кнопка **Проверить** повторно сверяет активные подписки Авито с текущим
   webhook-токеном Service2. **Переподключить Авито** создаёт новый токен,
   регистрирует новый URL и после подтверждения удаляет старые подписки Service2
   для этого подключения.
5. Если webhook не доставил сообщение, кнопка **Синхронизировать сообщения**
   запрашивает последние чаты и сообщения напрямую через Messenger API, не
   помечает чат прочитанным и идемпотентно добавляет только отсутствующие
   входящие сообщения за последние 48 часов. Это одновременно аварийный
   recovery-путь и диагностика: если прямое чтение возвращает 402/403, это отдельный отказ доступа к чтению.
   402 и 403 не доказывают конкретный тариф или право отправки; сохраняйте код
   ответа и различайте чтение, исходящую очередь и регистрацию webhook.

Webhook-токен не показывается пользователю и не хранится в открытом виде:
Service2 хранит только его хеш. Секретная часть URL появляется только в памяти
на время регистрации и проверки. Service2 маскирует этот сегмент в собственном
`django.request` error-log до записи на диск. Reverse proxy и APM также должны
маскировать callback URL в access/error-логах; URL нельзя публиковать или
добавлять в Git.

Секреты и временный access token хранятся только в зашифрованном виде. Для
стабильной расшифровки при ротации Django `SECRET_KEY` задайте отдельный
`COMMUNICATION_CREDENTIAL_KEY` одинаково на всех экземплярах приложения.

## Входящие и исходящие сообщения

Для каждого нового входящего диалога Service2 автоматически создаёт карточку
клиента или использует однозначно найденную карточку этой же организации.
Один Avito author ID в нескольких чатах одной организации связан с одним
клиентом; совпадение имени само по себе не считается идентификатором.
Повтор сообщения не создаёт новую карточку и не воспроизводит старые изменения
имени. Ручные поля имеют приоритет перед последующим автоматическим заполнением.

Из входящего текста детерминированно извлекаются телефоны, email и явно
обозначенные имя («Меня зовут», «Имя», «ФИО»), адрес и компания. Телефоны/email
добавляются в контакты с источником и ссылкой на диалог; адрес/компания и
сообщение-источник доступны в карточке клиента. Исходящие сообщения сотрудников
не используются для заполнения клиента. Цены, номера заказов и объявлений не
распознаются как телефон.

Имя покупателя и контекст объявления читаются через Messenger API в отдельном
процессе после фиксации входящего сообщения. Webhook не ждёт внешнего запроса.
Перед применением ответа повторно проверяются организация, подключение,
аккаунт, автор и привязанный клиент. Карточка объявления показывает сохранённые
название, цену, фото и ссылку, если их вернул Avito. Ошибка чтения не мешает
сохранить диалог и контакты. На странице диалогов нет технической панели
исходящей очереди; диагностика остаётся в административном разделе Авито.

Существующие диалоги обрабатываются фоном при открытии коммуникаций. Для
старого диалога без устойчивого ID автора и без однозначной CRM-привязки
создание карточки ждёт сведений о покупателе из Avito: это предотвращает
появление нескольких карточек одного автора до загрузки его профиля.
Неизвестные или неоднозначные связи автоматически не объединяются.
Для
контролируемой обработки сохранённых данных также есть команда
`enrich_communication_clients --ids <conversation-id>[,...]`: до 20 диалогов,
сначала локальные карточки, затем не более пяти внешних запросов метаданных.
Сетевая ошибка повторно проверяется при следующем запуске не раньше чем через
пять минут; успешный контекст обновляется не чаще раза в сутки. Миграция только
добавляет совместимые nullable-поля и индекс, без сети и массового backfill.

Webhook проверяет секрет URL, тип события и ID подключённого аккаунта, игнорирует отражённые
исходящие события и идемпотентно сохраняет входящие сообщения по Avito message
ID. Авторизованный webhook всегда отвечает HTTP 200, включая игнорируемые и
санитизированно ошибочные события: это соответствует контракту доставки Avito и
не провоцирует отключение подписки из-за ответа 201/4xx на валидный callback.
На странице **Каналы связи** сохраняются только безопасные диагностические поля:
время и результат последнего webhook и код последней ошибки без payload и без
webhook-токена.

Новый явно отправленный менеджером ответ услуг сначала сохраняется в текущей
транзакции. Только после её успешного commit вызывается обработка именно этой
записи. Внешний POST не выполняется под открытой транзакцией. Тихие часы
уведомлений владельцу не задерживают его ответ клиенту.

Для подключения 4 первое новое действие создаёт границу допуска будущих
ответов. Уже накопленная очередь до этой границы не рассылается. Существующее
явное отключение исходящих сохраняется. Другие подключения автоматически
не настраиваются.

Периодический резервный запуск использует только явное подключение:

```bash
python manage.py send_avito_outbox --connection-id 4 --limit 10 --periodic
```

Без --connection-id команда отказывается работать. --status читает только
сохранённую диагностику; --reconcile-only --message-id выполняет только
ограниченное чтение истории Авито. Регистрация webhook, доступ чтения,
исходящая очередь и состояние отдельного ответа показываются раздельно.

Каждая строка атомарно переходит из pending в sending под блокировкой строки.
Параллельные новые ответы могут обрабатываться независимо; повтор одного
ответа не выполняет второй POST. Успешный ответ с ID означает «Принято Авито»,
а не прочтение клиентом. Ошибка сети после начала POST, 5xx, перенаправление,
неполный или некорректный ответ остаются с неизвестным результатом; слепого
повтора нет. Авторизация не передаётся через перенаправление POST.

Старую явно выбранную запись разрешено завершать только после полной сверки
доступной истории и проверок её текущего контекста. Частичная история,
несколько совпадений или более ранний похожий ответ не доказывают результат.
Состоявшееся совпадение записывается в исходную строку, копия не создаётся.
Сохранённое намерение с неизвестным результатом POST не становится безопасным
для повтора из-за отсутствия сообщения в очередной выборке API.

В диагностике доступны последний запуск и успех, отдельный факт периодического
запуска, размер и возраст очереди, удержанные старые записи, неизвестные
результаты и ошибки. Успешный post-commit вызов не считается доказательством
работы cron. 401 означает отказ авторизации, 402 — требование оплаты/доступа
без предположения о конкретном плане, 403 — отказ доступа без автоматического
объяснения тарифом.

Вложения в исходящих сообщениях пока отклоняются до сохранения ответа:
наличие файла в Service2 не означает его отправку в Авито.
