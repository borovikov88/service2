# Авито: данные аккаунтов, объявления и диагностика API

Путь: **Авито** в меню Service2, URL `/avito/`. Раздел продолжает интеграцию
«Коммуникации → Каналы связи» и использует существующие зашифрованные
`AvitoCredential` и `ChannelConnection` текущей организации. Ключи повторно
вводить не нужно. Данные разных подключений не объединяются.

## Реализованные возможности

- Выбор подключённого аккаунта; переход к настройкам и существующим диалогам.
- Профиль: ID, имя и безопасная ссылка на профиль, если API их возвращает.
- Объявления: реальные ID, заголовки, статус, цена, категория, адрес и ссылка;
  по 50 записей на страницу, фильтр статуса и живой поиск в загруженной странице.
  «Все статусы» явно передаёт все пять статусов: без этого Avito по умолчанию
  возвращает только `active`. Если API не вернул общее количество, интерфейс
  не придумывает его. Ключи сотрудника могут вернуть пустой список при наличии
  объявлений у компании: это ограничение owner-only метода, а не доказательство
  отсутствия объявлений.
- Карточка объявления: сроки публикации, ID автозагрузки, применённые услуги
  и их расписание. Читается только объявление из загруженной страницы аккаунта.
- Доступные цены продвижения и значки для выбранного объявления. Это чтение
  цен в рублях; кнопок покупки/применения услуг нет.
- **Аналитика Авито v2**: период в пределах последних 270 дней, группировки
  итогов/объявлений/дней/недель/месяцев и постраничный ответ. Запрашиваются все
  35 метрик, перечисленных в переданной спецификации: показы, просмотры,
  контакты и их виды, избранное, конверсии, расходы, публикации и доступные
  отраслевые счётчики. Недоступные метрики API пропускает; интерфейс показывает
  «Нет данных», а не ноль. Отношения «контакты / просмотры × 100» и
  «просмотры / показы × 100» вычисляет Service2 из числителя и знаменателя одной
  группы, с округлением до двух знаков; их источник явно указан. При нулевом или
  отсутствующем знаменателе результат неизвестен. Исходный масштаб процентов
  Avito не угадывается. Прочие неподтверждённые конверсии и средние стоимости
  не отображаются. Исправление применяется при показе уже сохранённых снимков
  без нового API-запроса и без перезаписи исходного снимка.
  Значения разных групп не складываются в мнимое количество уникальных людей. ID временных групп показывается как ID: формат
  и часовой пояс этого идентификатора не угадываются.
- Статистика звонков Авито за период для объявлений текущей загруженной страницы.
  Отдельно обозначаются записи без атрибуции к объявлению (`itemId=0`).
  Итоги — сумма возвращённых счётчиков; это не статистика всех объявлений
  аккаунта. Пустой ответ не превращается в нулевые счётчики. По контракту `days`
  и поля `CallsStatsDay` необязательны: такие ответы принимаются, но отсутствующие
  даты/счётчики и зависящие от них итоги показываются неизвестными. Некорректные
  типы, чужие объявления и даты вне запрошенного периода дают отдельные безопасные
  коды ошибки без исходного payload.
- Баланс: реальные деньги и бонусы отдельно. Отсутствующее поле не становится
  нулём; валидный нулевой баланс показывается как ноль.
- Последняя успешная автозагрузка v4: распознанные ID, статус, даты и счётчики.
  Неизвестная схема ответа явно отмечается ошибкой, а не «пустым отчётом».
- Аналитика **импортированных данных Service2**: новые локальные диалоги,
  принятые входящие и доставленные исходящие сообщения за выбранный период.
  Используются даты создания/приёма в Service2 и `COMMUNICATION_TIME_ZONE`.
  Отложенные/ошибочные исходящие сообщения не считаются доставленными.
  Полнота импорта неизвестна: эти числа не являются статистикой показов,
  обращений или продаж Авито. Число открытых диалогов относится к текущему
  состоянию, а не к выбранному периоду. Для метрик дополнительно требуется
  `can_view_conversations`.
- Ручная диагностика в **настройках выбранного подключения**, отдельно от
  рабочего кабинета: авторизация, аккаунт, Messenger,
  webhook, объявления, баланс и автозагрузка.

## Обновление и ошибки

На GET страницы нет обращений к Авито. «Обновить данные» и отдельные кнопки
разделов отправляют CSRF-защищённый POST в Service2. Перелистывание объявлений
и фильтр статуса также явно запрашивают новую страницу через POST.
Все используемые внешние методы только читают данные. Аналитика и звонки имеют
свои ручные формы периода; общее обновление охватывает профиль, баланс, список
объявлений и автозагрузку. POST-методы статистики/цен не покупают услуги.

Перед чтением проверяется реальный ID аккаунта по ключам. Несовпадение с
`ChannelConnection.external_id` блокирует загрузку остальных разделов.
ID не исправляется автоматически. Одно подключение защищено от параллельных
обновлений короткой блокировкой в БД с автоматическим истечением через 3 минуты.
Серверный `AvitoApiThrottle` дополнительно ограничивает аккаунт+метод во всех
процессах/пользователях/дублирующих подключениях: статистика v2 — один запрос
в 60 секунд, список объявлений — не чаще одного в 3 секунды (в рамках лимита
25 в минуту). Торможение работает и при выключенном JavaScript; ключ строки
представляет SHA-256 аккаунта/метода, без чужих снимков или секретов.
Таблица создаётся миграцией `0133_avito_api_throttle`. На production она
применяется только через отдельно разрешённый штатный deployment.
Изменение ID подключения или более новый запрос не позволяет старому запросу
перезаписать результат. Существующие webhook-настройки сохраняются.

У каждого раздела есть время попытки и последнего успешного снимка. Ошибка
одного метода не скрывает доступные данные других. При ошибке старый снимок
сохраняется и явно помечается устаревшим, включая его исходную страницу и фильтр.
402/403 не означает доказанную причину отказа: возможны права или условия тарифа.
404 — метод/данные не найдены; 429 — ограничение частоты. Неизвестные ответы,
отсутствующее значение и валидные пустые данные различаются.

Сохраняется только ограниченный набор полей в
`ChannelConnection.settings.avito_workspace`. Там нет полных ответов API,
ключей, access token, телефона/email профиля, текста сообщений или секретных
webhook URL. Ссылки разрешены только на HTTPS `avito.ru`/`www.avito.ru`, без
credentials и query-параметров. Данные выводятся с HTML-экранированием.

## Внешние методы

| Метод | Использование |
| --- | --- |
| `GET /core/v1/accounts/self` | Проверка владельца ключей и данные профиля |
| `GET /core/v1/items?per_page=50&page=N&status=...` | Страница объявлений; `status` необязателен |
| `GET /core/v1/accounts/{id}/balance/` | Деньги и бонусы |
| `GET /autoload/v4/uploads/last_successful` | Последняя успешная автозагрузка |
| `GET /core/v1/accounts/{id}/items/{item_id}/` | Сроки и применённые услуги объявления |
| `POST /core/v1/accounts/{id}/vas/prices` | Только чтение цен продвижения и значков |
| `POST /stats/v2/accounts/{id}/items` | Показатели профиля, группировка и пагинация |
| `POST /core/v1/accounts/{id}/calls/stats/` | Счётчики звонков по загруженным объявлениям |
| `GET /messenger/v2/accounts/{id}/chats?limit=1&offset=0` | Диагностика чтения Messenger |
| `POST /messenger/v1/subscriptions` | Только чтение списка webhook |

Диагностика дополнительно проверяет получение/переиспользование токена через
существующий клиент. `POST /messenger/v1/subscriptions` — read-only метод
провайдера, он не регистрирует подписки. Диагностические результаты хранятся
отдельно от рабочих снимков: `avito_api_checked_at`, `avito_api_results`,
`avito_api_account_id`.

## Явные границы текущей версии

Это не покрытие всех семейств Avito API. Не реализованы:

- детальная разбивка расходов по услугам через отдельный
  `/stats/v2/accounts/{id}/spendings`: описание этого метода говорит «копейки»,
  а schema — «рубли». До уточнения денежные суммы оттуда не выводятся.
  Денежные `*Spending`, `commission` и отраслевые `*Price` в реализованной
  статистике v2 переводятся из копеек только там, где единица указана явно.
  Средняя цена просмотра/контакта и бонусы с неподтверждённой единицей скрыты;
  они не подменяются рублями или нулями;
- тариф/подписка и дата продления: эти сведения не выводятся из 402/403;
- создание, редактирование, публикация/снятие объявлений, изменение цен,
  покупка продвижения, пополнение баланса;
- загрузка файлов/изменение фида, запуск автозагрузки и её полный построчный
  отчёт;
- плановый мониторинг и уведомления. Обновление сейчас ручное;
- произвольные отраслевые API (доставка, недвижимость, вакансии и другие).

Источник новых контрактов: предоставленный пользователем 8 октября 2026
OpenAPI 3.0 «Объявления», SHA-256
`4d1e729c6ba89a4dc253dacc6591742bf702ebade8ee03bcb95abf23d9bd3018`.
Форматы проверены по `AnalyticsRequest`, `AnalyticsResponse`, `ItemInfoAvito`,
`VasPricesResp`, `CallsStatsRequest/Response`. Четыре операции изменения
объявлений/цен/продвижения из этого файла намеренно не вызываются.
Статистика v1 является альтернативным контрактом со своими `uniq*` полями;
реализация v2 использует её собственные валидные `views/contacts/favorites`.

Рабочие production-ключи не использовались для разработки/тестов. До заявления
о проверенной работе конкретных аккаунтов требуется ручная read-only проверка
их фактических ответов после разрешённого развёртывания. Неожиданная схема
баланса/автозагрузки должна уточняться по официальной спецификации или
санитизированному ответу без секретов.

## Проверки

`python manage.py test pool_service.tests.test_avito_management pool_service.tests.test_avito_workspace pool_service.tests.test_avito_analytics pool_service.tests_communications --settings=service_site.test_settings`

Тесты используют синтетические ответы: права/изоляция/CSRF, отсутствие сети на
GET, безопасные поля и ссылки, отличие нуля от отсутствия данных, пагинация,
частичный отказ, сохранение последнего успешного снимка, несовпадение ID,
конкурентное редактирование подключения, release блокировки и локальные метрики.
Также проверяются формат v2, единицы, отсутствующие метрики, серверный rate-limit
для дублирующих подключений, ownership карточки, read-only цены и partial failure
при оборванном HTTP-теле. `IncompleteRead`/transport errors санитизируются;
для отправки сообщения сохраняется неопределённость доставки без слепого retry.
После UI-изменений также проверяются шаблоны и состояния интерфейса.

## Регрессии, найденные при live-проверке

Тесты `test_avito_live_regressions.py` проверяют анонимные числовые примеры
масштаба процентов, независимые группы, нулевые/отсутствующие знаменатели,
отображение старого снимка без сети и sparse-ответы звонков. Подтверждённый
contract mismatch по необязательным полям исправлен; точная форма прежнего
ошибочного ответа не извлекалась. После выпуска требуется один согласованный
ручной запрос звонков, чтобы проверить реальную совместимость исправления.

## Компактный интерфейс и контекст объявления

«Подробнее» возвращает к выбранной строке через `item_id` и фиксированный
fragment-якорь; сведения и цены раскрываются непосредственно под объявлением.
Старые сведения/цены другого объявления не выдаются за данные выбранного.
Названия известных услуг берутся из переданного контракта Авито; неизвестный
код сохраняется как код без придуманного обещания. «Цена услуг» заменена явным
названием платного продвижения в Авито; чтение прайса ничего не покупает.
Старая цена зачёркивается только при отличии числовых сумм после одинакового
округления до двух знаков. Статусы показаны по-русски; даты с часовым поясом
форматируются в настроенной зоне, а для дат без зоны неопределённость обозначена.

Диагностика API перенесена в `communication_connection_edit`: те же
`can_manage_channels`, проверка организации, CSRF и no-store. Форма проверки
находится вне формы credentials; диагностический POST возвращает к якорю
`avito-api-diagnostics` и не принимает/не меняет поля ключей.

## Автоматический контроль статусов

Согласованный отдельный этап: `monitor_avito_statuses` работает на сервере
Service2 независимо от открытого чата. Нативный cron хостинга вызывает
существующий ограниченный worker каждые 15 минут. GitHub используется для
защищённого deployment и ручного запуска, но не для регулярных проверок. В БД успешная проверка сдвигает сохранённый срок на целое число часов
до ближайшего будущего срока, без дрейфа из-за длительности работы; ошибка — через 15, 30 и далее 60 минут. При занятом worker/deployment пропущенный tick повторяется по расписанию;
сбой cron/хостинга не маскируется успешным сканированием. Регистрация cron
выполняется отдельно через поддерживаемую панель/явный setup, фактическая работа
доказывается автоматическим первым снимком. Обычный deployment проверяет только
код/runtime и не требует внешней cron-liveness.
См. `docs/ai/deployment.md`.

Включение — CSRF-защищённый POST из **настроек конкретного подключения**,
«Включить контроль для меня». Получатель берётся только из `request.user`;
требуются действующая роль `owner` или `admin` этой организации и уже имеющееся
`can_manage_channels`. Это подписка только для текущего пользователя: другой
администратор или владелец не может сменить адресата, отключить или перехватить
существующую подписку, даже отключённую. Manager/сотрудник и superuser без
членства с нужной ролью не могут включить контроль. Произвольный recipient
из формы не принимается. Перед каждым сканированием и перед фиксацией результата роль,
активность пользователя/подключения, организация и Avito account ID проверяются
заново. Утрата роли/членства/доступа или смена подключения останавливает монитор
до явного включения тем же получателем.
Подключения товаров и услуг включаются независимо. Никаких новых ключей,
webhook, тарифов, прав или изменений объявлений нет.

Первый **полный успешный** обход создаёт базовый снимок без уведомлений.
Повторное включение после остановки начинает новую базу, чтобы не присылать
исторические события за период отключения. Новые неизвестные ID также получают
только исходный статус. Дальше уведомления возникают при известных переходах
в `removed`, `old`, `blocked`, `rejected` из supplied Item OpenAPI; не вводится
вымышленный API-статус `archived`. Отсутствующий в ответе ID никогда не считается
снятым. Недокументированные/неизвестные статусы считаются ошибкой, не событием.

Пагинация читает `per_page=50` со всеми пятью статусами; максимум 100 страниц
и 420 секунд на аккаунт. Без `meta.total` требуется короткая/пустая последняя
страница; если total присутствует, количество и согласованность проверяются.
Повторные ID, неверная страница, избыточный ответ, неизвестный статус, обрыв,
противоречивый total и достижение лимита делают **весь** обход неуспешным.
Старые статусы, база и время успешного снимка не меняются; ошибок API в ленте
изменений объявлений нет. Используется тот же `AvitoApiThrottle` account+items,
не чаще запроса в 3 секунды (ниже лимита 25/min); конкурирующая ручная работа
также расходует этот бюджет. Полнота относится к доступному этим ключам ответу
Avito: employee-key API может вернуть пустой список, что не доказывает отсутствие
объявлений у компании.

`AvitoStatusMonitor` хранит адресата, привязку аккаунта, базу, времена попытки,
последнего успеха/сбоя, следующий срок и санитизированный код ошибки.
`AvitoListingStatus` сохраняет только ID, статус, номер перехода и время чтения,
без полного ответа или текста объявления. Заголовок используется только в
адресном уведомлении. Блокировка строки + lease исключают параллельные результаты;
изменение lease/подключения отменяет устаревший результат. Изменения статусов и
`Notification` фиксируются одной транзакцией. Дедупликация включает монитор,
поколение базового снимка, ID объявления и номер перехода, поэтому повторный
запуск не дублирует сообщение, а повторное отключение после восстановления
даёт новое событие. Используется существующий `notify_users` только для одного
подписавшегося пользователя с `send_push=False`; действующая настройка отключения in-app уведомлений
уважается. Нет email, push, сообщений сотрудникам/клиентам или в Avito.

Настройки показывают получателя, базу, последнюю попытку/полный успех/ошибку,
число страниц/объявлений и следующий срок. «Запросить проверку» ставит задачу
на ближайший серверный tick и не обходит общий rate limit. GET не обращается
к Avito. CLI `--status` читает только агрегированные счётчики, без персональных
данных, ID аккаунтов, заголовков или секретов; вывод подходит для публичных logs.

Миграция `0134_avito_status_monitor` добавляет две отдельные пустые таблицы,
индекс и unique constraint; existing rows/credentials/notifications не меняются.
Rollback к прежнему коду совместим с оставшимися additive tables. Обратная
миграция удалит только данные монитора и требует отдельного решения; обычный
roll-forward предпочтительнее. До проверки регистрации cron, включения обеих подписок и первого полного
автоматического baseline наличие deployed command не означает работающий мониторинг.


### Совместимость с существующей ролью администратора

При live-проверке обнаружено, что аккаунт, для которого запрошены уведомления,
использует существующую роль администратора организации, а не буквальный
`owner`. Ограничение только по `owner` было лишним и скрывало настройку.
Исправление сохраняет текущие права чтения/управления каналами и позволяет
owner/admin подписать только себя. Роли, разрешения, scope и данные доступа
не меняются; имя/ID пользователя не зашиты в код. Адресат существующей подписки
неизменяем для коллег; автоматические проверки уведомляют только сохранённого
подписчика, проверяя его действующий доступ. Исторические события не рассылаются.


### Неподтверждённое расписание

Настройки показывают состояние серверного worker: неподтверждённый, выполняется,
ошибка, устаревший или подтверждённый завершённый запуск. Только реальный tick,
успешно завершивший worker, может дать свежую отметку; простые GET и deployment
её не создают. До свежего успеха новая активация блокируется. Уже активная
подписка при деградации сохраняется, с явным предупреждением; provider retry и
данные последнего полного scan не меняются. В этих же защищённых настройках
доступна точная команда для панели CronTab с путями установленного приложения,
без secrets и без чтения/изменения существующей таблицы cron.


## Подготовка к аудиту объявлений

Кнопка «Проверить весь список» отдельно от общего обновления выполняет только
GET-запросы с сохранёнными ключами выбранного подключения. Используется тот же
валидированный full scan, что и у контроля статусов: проверка аккаунта, общий
DB throttle, все страницы пяти статусов Item API, строгие ID/пагинация/total.
Ручной scan имеет бюджет 60 секунд; scheduled scan сохраняет прежние 420 секунд.
Неполный обход или неизвестный статус не сохраняется как успешный/нулевой список.
Предыдущий отчёт и его время сохраняются с отметкой устаревших данных.

Отчёт содержит итог по статусам и кандидатов среди активных объявлений с
одинаковым названием после нормализации Unicode, регистра и пробелов.
Это не доказанные дубли: совпадение названия требует сверки товара, варианта
и XML ID. Сохраняются только итоговые числа и до 25 групп по 10 ID/название;
все дополнительные группы/ID учтены в итогах и явно отмечены как не показанные.
Пустой полный scan является подтверждённым нулём только в пределах Item API.

Полный обход Item API не доказывает полноту неопубликованных/архивных записей
из кабинета Авито, не проверяет XML, три правила OpenCart, остатки, ТН ВЭД или
причины автозагрузки/снятия/истечения. Эти проверки отмечены как невыполненные.
XML сайта остаётся источником публикации. Provider writes, удаление, автоправки,
продвижение, новые подписки и изменение доставки уведомлений сюда не входят.
