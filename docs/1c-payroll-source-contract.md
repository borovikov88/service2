# ФОТ: наблюдаемая схема источника и проверка месяца

## Что подтверждено

9 сентября 2026 владелец выполнил диагностический скрипт из commit
`2cd9c7f0796690e879cf4a59bf8db0f154b3a704` на действующем hosting service2.
Проверка SHA256 прошла; получена `$metadata` 1С с четырьмя явно выбранными
сущностями и `truncated=false`. Это свидетельство структуры источника,
полученное через терминал владельца; агент не получил прямой доступ к 1С.

Для читателя подтверждены следующие технические поля. В таблицах нет
значений рабочих строк или персональных данных.

### `AccumulationRegister_НачисленияИУдержания_RecordType`

| Поле | Тип в metadata | Использование при сверке |
| --- | --- | --- |
| `Recorder`, `Recorder_Type` | `Edm.String` | Идентификация движения вместе с номером строки |
| `LineNumber` | `Edm.Int64` | Контроль повторов |
| `Active` | `Edm.Boolean` | Только активные движения |
| `Period` | `Edm.DateTime` | Сравнение месяца движения с периодом регистрации |
| `ПериодРегистрации` | `Edm.DateTime` | Явная основа фильтра первого preview; смысл требует сверки |
| `Организация_Key` | `Edm.Guid` | Проверка allowlist и раздельные итоги |
| `Сотрудник_Key` | `Edm.Guid` | Проверка структуры строки, без вывода идентификатора |
| `СтруктурнаяЕдиница_Key` | `Edm.Guid` | Измерение подразделения |
| `Валюта_Key` | `Edm.Guid` | Раздельные итоги, без угадывания валюты |
| `ВидНачисленияУдержания_Key` | `Edm.Guid` | Точечное получение типа из справочника |
| `Сумма`, `СуммаВал` | `Edm.Double` | Два отдельных ресурса, без автоматической конвертации |

Также опубликованы `Операция_Key`, `Номенклатура_Key`, `ДатаНачала`,
`ДатаОкончания`, `ОтработаноДней`, `ОтработаноЧасов`, `Размер`.
Они не требуются для первого агрегатного чтения.

### `AccumulationRegister_РасчетыСПерсоналом_RecordType`

Имеет те же поля идентификации, активности, двух дат, организации,
сотрудника, подразделения, валюты и двух сумм. Вместо вида начисления
используется `RecordType` (`Edm.String`). Подтверждено также поле
`СодержаниеПроводки`, но reader его не запрашивает.

Первый preview группирует движения по фактическим `RecordType` и
`Recorder_Type`; не объявляет их автоматически начислениями или выплатами.
Начальные и конечные остатки без чтения истории или подтверждённого
контракта остатков из этих строк не выводятся.

### `Catalog_ВидыНачисленийИУдержаний`

| Поле | Тип | Использование |
| --- | --- | --- |
| `Ref_Key` | `Edm.Guid` | Только идентификаторы, использованные выбранными движениями |
| `Тип` | `Edm.String` | Фактическая группировка, без заранее угаданных значений |
| `IsFolder`, `DeletionMark` | `Edm.Boolean` | Проверка пригодности элемента справочника |

Справочник также публикует `Description`, `Формула` и другие реквизиты.
Они не нужны для первого preview и не запрашиваются. Значения `Тип`
в рабочем источнике ещё не получены. Нельзя классифицировать начисления
по тексту произвольного наименования или считать неизвестный вид нулём.

### `Document_НачислениеЗарплатыУНФ`

В metadata подтверждены `Posted`, `DeletionMark`, `ПериодРегистрации`,
`Организация_Key`, `СтруктурнаяЕдиница_Key`, `СуммаДокумента` и раздельные
табличные части `НачисленияУдержания`, `НалогиНаДоходы`, `Взносы`,
`ПогашениеЗаймов`, `ПримененныеВычетыПоНДФЛ`. Строки начислений содержат
сотрудника, вид начисления/удержания и сумму. Первый reader читает регистры,
а не эти документы. `СуммаДокумента` не выбрана как готовый ФОТ.

## Первый месячный preview

`pool_service/finance_imports/odata_payroll.py` — отдельный reader без Django
и БД, пригодный для запуска одним проверенным файлом из существующего venv.
Он использует только HTTPS GET, `ONEC_ODATA_*` и существующие настройки
доверенных сертификатов. Не создаёт import batch, snapshot или строки ФОТ.

Месяц обязателен (`--month YYYY-MM`), организации ограничены настроенным
`ONEC_ODATA_ORGANIZATION_GUIDS`; дополнительный выбор может только сузить
этот список. Фильтры повторно проверяются в каждой полученной строке.
Это необходимо, поскольку ранее фильтрация OData на этом проекте уже
возвращала данные вне запрошенного периода.

Переходы по страницам сохраняют исходные `$select`, `$filter` и `$format`;
добавлять `$expand`, произвольные query options или другой источник нельзя.
Лимиты reader: суммарно 16 МиБ ответа, 50 000 строк и 100 страниц;
тайм-аут сокета 15 секунд. Отдельный Linux CLI дополнительно ограничен
60 секундами целиком через alarm. При будущей интеграции функции в Django
нужно отдельно обеспечить общий срок выполнения: проверки между чтениями
и socket timeout не заменяют deadline для медленно поступающего ответа.

JSON-числа читаются непосредственно в `Decimal`: это не восстанавливает
точность, утраченную на стороне 1С, но не добавляет преобразование через
Python float. Отрицательные суммы сохраняются для анализа сторно.
Разные валюты не суммируются в один показатель; `Сумма` и `СуммаВал`
остаются раздельными. Пустой или неполный ответ не выдаётся за нулевой ФОТ.

В stdout только агрегаты, количество строк и технические признаки сверки;
нет фамилий, идентификаторов сотрудников, документов, формул и строк
начислений. Выгрузки и реальные месячные суммы не сохраняются в Git.

## Что ещё требуется до автоматического импорта

- Получить реальный месячный preview и значения типов начислений/удержаний.
- Сверить период, состав организаций/валют и итог с соответствующим отчётом 1С.
- Подтвердить обработку сторно, удержаний и поздних перерасчётов.
- Выбрать подтверждённый источник выплат и остатков либо явно отделить
  импорт только начислений от старого четырёхколоночного payroll-контракта.
- Реализовать источник OData в сервисах ФОТ, версии, отсутствие дублей,
  права и организационную изоляцию; провести независимое ревью и проверки.

Официальная [страница 1С:УНФ по зарплате](https://v8.1c.ru/small.biz/zarplata-i-personal/)
описывает учёт по видам начислений и удержаний и пользовательские формулы.
Она не заменяет проверку конкретной OData-схемы, значений её типов и
методики действующего отчёта владельца.
